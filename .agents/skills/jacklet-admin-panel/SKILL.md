# Admin panel

The panel reads and writes tracker credentials, so most of what follows is about who can reach it and what it must never reveal. Read the entry for a behavior before changing it.

## Signing in

- **The panel is off unless a password is set**: `admin.New` takes an `*admin.Password` built from `JACKLET_ADMIN_PASSWORD`/`JACKLET_ADMIN_PASSWORD_HASH`, and `Enabled` reports false when neither is set; `jacklet.Stack.Routes` registers no `/admin` routes in that case, so every path 404s. The panel reads and writes tracker credentials, so "no password configured" must mean "no panel", never "an open panel".
- **Prefer a hashed admin password**: `JACKLET_ADMIN_PASSWORD_HASH` holds a PBKDF2-HMAC-SHA256 hash (`pbkdf2-sha256$<iterations>$<salt>$<key>`, stdlib `crypto/pbkdf2` — no new dependency), generated by `jacklet hash-password`, and takes precedence over the plaintext `JACKLET_ADMIN_PASSWORD`. The hash records its own iteration count so raising `hashIterations` doesn't invalidate hashes already deployed. A malformed hash fails startup rather than falling back: quietly ignoring it would leave the panel accepting a different password, or none. `hash-password` reads from stdin, never from an argument, since arguments are visible to every process on the machine. Hashing does not protect the plaintext path — the value is in the process environment either way — it protects against the password being disclosed in a compose file, a unit file, or a pasted bug report.
- **The panel authenticates with sessions, not `JACKLET_API_KEY`**: `pkg/admin/session.go` issues a random 256-bit token in an `HttpOnly`, `SameSite=Lax` cookie scoped to the panel's prefix. It is `Secure` when the request arrived over TLS or when an HTTPS `JACKLET_BASE_URL` says a reverse proxy terminates TLS; leaving that setting empty preserves plain-HTTP deployments. `guard` requires a session for every route and a matching CSRF token for every non-GET. A request whose token has no session — aged out past `sessionLifetime`/`sessionIdleTimeout`, or held over a restart, since the store is in memory — has its cookie cleared and is sent to the prefix's `/login` with a 303, which the browser follows with a GET whatever method it started as. A GET carries its path along as `?next=`, so signing in returns to the page that was asked for; `safeNext` admits only a path inside the prefix, cleaned in its decoded form, since an escaped `%2e%2e` survives `path.Clean` untouched while still walking a directory up in the browser. A non-GET carries nothing, because a browser following a redirect can only ask for a page again with a GET. `JACKLET_API_KEY` travels in a query string, which is fine for a machine API and unacceptable for a UI holding tracker passwords — don't merge the two.
- **Sign-in attempts are spaced per client address, and the slot is taken before the password is checked** (`loginLimiter`, `clientAddress`, `loginDelay`): a plaintext password verifies in microseconds, so a delay served after checking does nothing against parallel guesses, and a panel-wide lock held through that delay lets anyone who can reach the panel keep the administrator's own sign-in queued behind theirs. Reserving first admits one attempt per window per address and answers the rest with a 429 unchecked. The key is the host, an IPv4-mapped address read as its IPv4 form, and an IPv6 host reduced to its `/48`, because a client owns every address in its allocation and would otherwise get a fresh slot per guess. Expired entries are swept at most once per delay, so an attempt costs a constant amount however many addresses are tracked. A correct password releases its slot, and it also ends the session the request's cookie already names. The address is `r.RemoteAddr` unless it falls in `admin.Options.TrustedProxies` (`-trusted-proxies`/`JACKLET_TRUSTED_PROXIES`, parsed by `trustedProxyList`), when `forwardedClient` reads `X-Forwarded-For` **from the right**, skipping listed proxies and taking the first address that is not one: every entry left of that was written by the client and reading it would hand a guesser a fresh slot per request. A header on a request from an unlisted address is ignored, so with the list empty every client behind a proxy shares the proxy's slot.

## Serving the panel

- **The panel's mount path is `admin.Options.Prefix`** (`DefaultPrefix`, `/admin`, when empty): a library embedder can serve it anywhere, and routes, template links (through the `prefix` template function), redirects, the cookie scope and `safeNext` all read the one validated value (`ParsePrefix`), so they cannot disagree. An invalid prefix fails `NewWithOptions`, and `Admin.Prefix` reports the effective one. `cmd/jacklet` sets it from `-admin-prefix`/`JACKLET_ADMIN_PREFIX` (`settings.AdminPrefix`, default `DefaultPrefix`), so a malformed value fails startup like the other settings, and `TestRun_ServesTheAdminPanelUnderItsPrefix` pins the wiring through `run`. On Windows, `jacklet service config set AdminPrefix` refuses a malformed one through the same `ParsePrefix`; a prefix that collides with one of the server's own routes is found only at startup, since that takes the routes themselves.
- **A state-changing operation is a POST**: the manual search scrapes the tracker live, so it is `POST /admin/search` with a CSRF token rather than a bookmarkable GET. `SameSite=Lax` still sends the session cookie on a top-level GET navigation, so a side-effecting GET would be reachable from another site.

## Settings and secrets

- **Secrets are never rendered into a page**: `settingViews` substitutes `maskedSecret` for any stored credential (`isSecret` matches type `password` and names containing password/passkey/apikey/cookie/token/secret), and `handleSaveSettings` treats the mask submitted back as "keep what is stored". Rendering the real value would put tracker passwords in the DOM, in browser history, and in any page cache.
- **Config writes are atomic and owner-only**: `ConfigStore.Save` writes a temp file with mode 0600 and renames it into place, because the file holds credentials and a scrape may be reading it concurrently. Saving also invalidates the cached login for that tracker, since the credentials it was established with may have just changed. Saving a renamed tracker also removes the files saved under the ids its `replaces` lists, since the settings now live under its own id and an old file would otherwise stand in again whenever the tracker's own is empty. A file that could not be read is kept, since its settings were never carried over.
