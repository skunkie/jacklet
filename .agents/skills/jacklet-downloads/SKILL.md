# Downloads

A Torznab client has no session on a private tracker, so Jacklet fetches a torrent file with its own and passes it on, and hands a magnet to the client to resolve. Every request a download makes carries the tracker's session, which is why so much of what follows is about where those requests may go. Read the entry for a behavior before changing it.

## Torrent files and magnets

- **A torrent file and a magnet are separate columns**: a tracker commonly offers both, and Cardigann declares them as separate fields, so `torrents.magnet` sits beside `download_url` and the panel gives each its own column. `download` naming a magnet is stored as one, leaving `download_url` empty, since there is nothing to fetch through the tracker's session. An info hash alone becomes a magnet only for a definition whose `type` is `public` or `semi-private` (`isPubliclyShared`): such a link names no trackers unless the operator configured some (below), so a client reaches peers only through the DHT, which a private tracker's torrents are deliberately absent from, and it carries no passkey. Jackett applies the same restriction. **The built link is trackerless unless the operator supplies announce URLs**: Jackett's `MagnetUtil.InfoHashToPublicMagnet` appends a fixed list of ten public `tr=` announce URLs, so a client resolves it faster than through the DHT alone. Jacklet ships no such list, because third-party announce addresses go stale and every built magnet would advertise them; `JACKLET_MAGNET_TRACKERS`/`-magnet-trackers` (`scraper.Options.MagnetTrackers`, validated by `magnetTrackerList` so a typo fails startup) lets the operator own one, and each entry is appended as a `tr=` parameter by `torrentFrom`. Unset, the link is trackerless and reaches peers only through the DHT, which is a divergence from Jackett rather than parity. The list applies only to a magnet built from an info hash: a magnet a tracker supplied is passed on as it stands, and a private tracker still gets no built magnet. The list is written into a row at scrape time, so a change applies to rows scraped afterwards and leaves stored ones as they were; and since magnets are served to every client, only public announce URLs belong in it. The reverse direction, reading an info hash back out of a magnet (`magnetInfoHash`), has no such restriction: a hash taken from a link already in hand discloses nothing the link did not. Torznab advertises the magnet as the `magneturl` attribute (and `MagnetUri` in the JSON results) while `link` stays the proxied torrent file, so a client picks; a row with no torrent file has the magnet as its `link`, and its download endpoint redirects to it rather than fetching.
- **Downloads are proxied, not handed off**: `GET /api/v2.0/indexers/{id}/download/{row}` (`Torznab.Download`) — Jacklet's own path, because Jackett serves the equivalent from `/dl/{indexerId}` keyed by an encrypted `path` parameter carrying the tracker's link, a payload only Jackett can mint; a client never builds this address anyway, it follows the one in the feed. It fetches the `.torrent` from the tracker using Jacklet's own authenticated session and serves it as `application/x-bittorrent`. The admin panel's result tables link to `GET /admin/indexers/{id}/download/{row}` (`Admin.handleDownload`) for the same reason; both resolve the row and then hand it to `torznab.ServeTorrent`, which decides nothing about who may ask — the Torznab endpoint checks `JACKLET_API_KEY`, the panel checks its session. A magnet is redirected rather than fetched, since the client resolves one itself, which is why `downloadPath` leaves it out of the panel's proxy links. A Torznab client has no account on a private tracker, so giving it the tracker's own link returns a 403 or a login page saved as a `.torrent`. `{row}` is the store's row id rather than a URL, so the endpoint resolves what to fetch from the database and cannot be pointed at an arbitrary address. The fetched body is capped at `defaultMaxDownloadBytes` (1 MiB) — a `.torrent` is a piece-hash list, well under a megabyte even for a large release, and without a cap a tracker or a compromised mirror could push arbitrary volume through the proxy to its clients. Unlike a scrape, exceeding it cannot fail the request: `ServeTorrent` streams the body straight out, so the headers are already sent and the only options left are to truncate and log.
- **A failed download tells the client only which indexer failed**: `ServeTorrent` answers `Failed to download from <indexer>` and logs the cause. The cause names the tracker's address, which on many trackers carries the passkey, and redaction recognizes only the shapes it knows (`pkg/scraper/redact.go`), so leaving the client out as a destination keeps a shape it misses from leaving the server. A refused foreign link keeps the tracker's text in the log too, for the same reason, though it answers with its own status and message (400, `Refused to download from <indexer>: the link leaves the tracker`), so a client can tell a refused link from an unreachable tracker.

## The download block

- **A definition's `download` block is followed as Jackett follows it** (`followDownloadBlock`, `pkg/scraper/downloadblock.go`): a row commonly stores a release's details page rather than its torrent file, and the block says how to get from one to the other — a `before` request first (a tracker's "thanks", or an API call; its path is a template, or is read off the release's page by `pathselector`), then either an `infohash` block building a magnet from a hash and title read off a page, or `selectors` tried in turn, the first whose link serves a torrent file winning, and otherwise the stored link itself. Without it, every download from such a tracker fetches the details page and is refused as a web page. Five things to know:
  - **Every request is made to the tracker** (`trackerSiteOf`): each goes out with the tracker's session, so the before request, the release's page and the selected link must each name one of the tracker's own hosts, as the stored link must. Jackett fetches wherever a definition points; here a selected link on another host is a refused download, deliberately. The torrent file's redirects are checked hop by hop as before, while a page's are followed as a search page's are, carrying only the cookies the jar holds for where they land.
  - **The pages a block reads are pages**: they are fetched by `fetch`, as a search page is — through FlareSolverr for a tracker that opted in, in the tracker's encoding, under the response cap — and only the torrent file is fetched directly. A page's own query string is kept and inputs are appended to it (`withQuery`), since a details page's release id lives there. The release's page is fetched once however many selectors read it, where Jackett fetches it again for each.
  - **`testlinktorrent` defaults to true**, as in Jackett (`Tracker.testsLinkTorrent`), so a selected link is kept only when its body starts with a bencoded dictionary's `d`, and otherwise the next selector gets its turn. A link answering with a web page is such a miss rather than a lapsed session, so `Download` clears the login only when the download as a whole ends on one (`errDownloadWebPage`). `keepIfTorrent` peeks the byte rather than consuming it, so the file is fetched once where Jackett fetches it twice.
  - **The before request's status does not stop the download**, as it does not in Jackett: a tracker may refuse a second "thanks" with an error status and serve the file anyway. Through FlareSolverr the same answer with no body leaves the browser on its error page (`errBrowserErrorPage`), which is taken the same way. Its answer is then an empty page. A before request the browser could not deliver at all, which that page names as a network error (`browserNetworkError`), is no answer from the tracker and fails the download.
  - **A magnet is an answer, not a host**: a selector reading one, an `infohash` block, and a tracker redirecting a download to one all yield `Download.Magnet`, which `ServeTorrent` redirects to as it does a stored magnet. An `infohash` magnet is built only from a value `isInfoHash` accepts, since the value is written into the link as it stands, and for a tracker of any type, unlike one built from a row's info hash, because the definition asks for it as the only download the tracker offers; it carries the operator's announce URLs like any other built magnet. A failed `infohash` block fails the download, where Jackett logs it and fetches the stored link, which for such a definition is a page.
  `.DownloadUri` (`downloadURIVars`) carries the stored link's parts under Jackett's names; `.DownloadUri.Query` renders whole as the query string and indexes by name as `.DownloadUri.Query.id`. The before request's path and inputs are rendered by `renderTemplateStrict`, so a variable the link lacks fails the download, as it does in Jackett, rather than sending `<no value>` to the tracker; selectors and filter arguments keep the lenient rendering. A selector reads its page as a field reads its row (`selectDownloadValue`), with the document's root element as the row, so `:root` is the whole page and a selector reads its first match. `download.headers` and a before request's `queryseparator` are not modeled, so a definition declaring either has it ignored.
