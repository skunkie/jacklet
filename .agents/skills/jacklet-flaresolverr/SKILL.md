# FlareSolverr

FlareSolverr drives a real browser through a tracker's anti-bot challenge. What it returns is the browser's page rather than the tracker's response, and what it keeps between requests is a browser session, so most of what follows is about the difference those two facts make. Read the entry for a behavior before changing it.

## Setup and opting in

- **FlareSolverr's address is normalized and checked at startup** (`FlareSolverrEndpoint`): FlareSolverr accepts a POST only at `/v1`, so the bare address its own documentation gives, `http://flaresolverr:8191`, has `/v1` added, an address that names it is used as it is, and a value that is not an http or https address fails startup like the other URL settings; the constructor applies the same normalization to a program embedding `pkg/scraper`. A reply that is not JSON names its HTTP status, so a wrong path reads as a 405 and not as a parse error. **A session is verified against `sessions.list` before every use** (`verifyFlareSolverrSession`), and not on a timer, because FlareSolverr creates a session on first use under any name it is given: after a restart or a crash the next request silently gets a fresh, empty browser under the old id, and everything Jacklet tied to the old one — the cookies it was sent, what it kept for downloads, the tracker's login — is stale. The question has to come before the request: a request naming a session FlareSolverr has lost makes a fresh one under that name, so a check made later would find the id listed and trust an empty browser. A session that FlareSolverr no longer lists is reset like a retired one, without a destroy, and a list that cannot be fetched leaves the session as it is. It costs one call that does no browser work beside each request that drives one.
- **A tracker uses FlareSolverr only when it opts in**: an endpoint (`JACKLET_FLARESOLVERR_URL`) makes FlareSolverr available and `flaresolverr: true` in the tracker's own config file (`FlareSolverrSetting`, `FlareSolverrOptedIn`, `usesFlareSolverr`) turns it on for that tracker, so a tracker with no challenge never drives a browser or holds a session. It is a **reserved override, not a definition setting** — nothing declares it, `mergedConfig` does not expose it to templates, and the admin panel offers it as its own checkbox (only when an endpoint is configured), which is why `handleSaveSettings` writes it itself and keeps it as it was when the checkbox is hidden: saving rebuilds the file from the definition's declared settings and would otherwise erase it. A scrape reads that file once and carries the answer in its context (`withFlareSolverrChoice`), so its many fetches do not parse it again. FlareSolverr's browser cannot see Jacklet's cookie jar, so the cookies the jar holds for a request's address, which is where a `method: cookie` login puts the operator's cookie, travel in the request's `cookies` list (`flareSolverrCookies`). FlareSolverr loads a page a second time whenever a request carries cookies, and a session keeps the ones it has been given, so they are sent only to a session that has not seen them or when they changed (`flareSession.cookies`, a fingerprint reset whenever the session is retired or evicted). **What comes back is the browser's page, not the tracker's response**, which matters in three ways, none of which FlareSolverr reports: JSON, and XML served as RSS or Atom, are wrapped in a page of its own with the text escaped inside a `<pre>`, so `unwrapBrowserDocument` takes it out again for a JSON or XML path (XML served as plain XML is shown through the browser's viewer, which keeps the document as real elements the XML reader already selects from, and needs nothing); a tracker that answers with an error status and no body leaves the browser on `chrome-error://`, which `scrapeWithFlareSolverr` fails with `errBrowserErrorPage` and does not count against the session, while a tracker the browser could not reach lands there too and fails with the network error the page names (`browserNetworkError`) instead; and an error status **with** a body looks like any other page, because FlareSolverr reports every status as 200, so `checkStatus` can only refuse a status a later FlareSolverr reports and such a page parses as no results. **A torrent file is never fetched through FlareSolverr**, since it returns a page as text and would corrupt the file, but the download presents the browser's identity: each request's reply carries the cookies the browser held and the user agent it presented, which the tracker's session keeps (`rememberFlareSolverrBrowser`, dropped when the session is retired or evicted), and `Download` reads them through a `layeredJar` in front of Jacklet's own, with the user agent (set after the definition's headers, which are never sent through FlareSolverr, so a declared `User-Agent` cannot replace the one the clearance is bound to), because a form login leaves the session in the browser's cookies and not in Jacklet's jar and a Cloudflare clearance is bound to the user agent that earned it. The cookies are loaded under the address the browser **landed** on (`browserPageURL`, from `solution.url`), not the one requested, because a tracker often redirects and a host-only cookie of the landing page does not match the requested address. A cookie for a bare IP address loses its domain on the way into a jar, which refuses one.

## Requests

- **FlareSolverr carries no per-request headers, and `warnUncarriedHeaders` says so**: `fetch` hands a FlareSolverr-backed search straight to `scrapeWithFlareSolverr`, before the branch that applies `search.headers`, the default User-Agent and the redirect policy — and that is not an oversight to tidy up. The request is made by a real browser, which supplies its own headers, and FlareSolverr v3 has no option to override them, so there is nothing to forward and forwarding it anyway would only look like support. Definitions declaring `search.headers` are common, so the silence was the problem: a warning is logged once per tracker (`scrapeState.hasWarnedFlareHeaders` — once per *tracker*, not per search, since a line repeated on every poll is one an operator stops reading). `SearchPath.FollowRedirect` is inert for the same reason, the browser following redirects itself. Torrent files bypass FlareSolverr and **do** apply the headers, so the two paths genuinely differ.
- **FlareSolverr mirrors the definition's HTTP method**: `scrapeWithFlareSolverr` issues `request.get` with the inputs in the query string for a `method: get` search path and `request.post` otherwise. Always POSTing means a GET definition's inputs never reach the tracker. FlareSolverr also gets its own `http.Client` (`flareSolverrTimeout`, 3m) rather than sharing the scraper's 30s one, since driving a browser through an anti-bot challenge routinely takes longer than a plain fetch. **Each tracker has its own FlareSolverr session and request slot** (`flareSessionFor`, `flareSession`): a session is a single browser tab and FlareSolverr takes no lock around it, so two requests on one at once would drive the same page, and the slot admits one request of a tracker at a time, taken with the request's context so the wait ends with it. Different trackers have different sessions and are driven at the same time, which is what lets the aggregate indexer scrape several at once, and a session carries one tracker's cookies, so a lapsed login, a failed challenge or a request that ran out of time is that tracker's problem alone. The number of live sessions is bounded (`Options.MaxFlareSolverrSessions`, `DefaultMaxFlareSolverrSessions`, set from `-flaresolverr-sessions`/`JACKLET_FLARESOLVERR_SESSIONS` by `flareSolverrSessionLimit`, which refuses less than 1) even though only opted-in trackers have one: each is a browser instance on the FlareSolverr host, and an aggregate search over many opted-in trackers would otherwise start one per tracker. `evictIdleFlareSolverrSessions` destroys the least recently used **idle** session to make room, never one whose slot is held, so the count can pass the limit by however many requests are running at once, and forgets the evicted tracker's login, whose cookies went with it. **The limit has to cover the trackers that use FlareSolverr**: an aggregate search visits them in the same order every time, which is the worst case for least-recently-used eviction, so with more of them than the limit every request finds its session just closed for the one before it and every search solves every challenge again. That is why each eviction is logged at info level with the tracker and the limit, and why the limit is a setting. Credentials and cookies of an opted-in tracker pass through FlareSolverr, which the configuration page says. FlareSolverr keeps a session's browser after an error, so a browser that has crashed fails every request until it is destroyed, while one failure is usually a challenge that did not solve in time and destroying the session then would throw away the clearance it holds. A session therefore survives one failure and is retired after `flareSessionMaxFailures` in a row (`noteFlareSolverrFailure`; a success ends the run), except for the "Cloudflare has blocked this request" answer, which says the address is banned and not that the browser is broken, and an unusable reply (`errFlareSolverrReply`: a page over the size cap, or an answer that is not FlareSolverr's at all), which belongs to the page and not the session. **There is no in-request retry**: FlareSolverr creates a session on first use under whatever name it is given, so a request naming a session it has lost never fails with a missing-session error, and there is nothing to retry on. Retiring (`retireFlareSolverrSession`) **destroys** the session, since FlareSolverr keeps a browser alive until told otherwise, on a context detached from the request (`flareSolverrDestroyTimeout`) so a canceled request cannot forget a session without destroying it, and only when it is still the tracker's current one, so a second request seeing the same failure does not destroy the replacement. It also forgets that tracker's login, because the session held its cookies and a cached login would otherwise send searches to a login page that parses as no results. A request is told to stop before its own deadline (`flareSolverrMaxTimeout`, `flareSolverrTimeoutMargin`): FlareSolverr enforces `maxTimeout` itself and answers with an ordinary error, so a slow challenge ends there and the session stays healthy, and a request that outlived its deadline is not still running in the tab. A request whose context was **canceled**, by a client that went away, may still be running in it, and the next request would navigate the same tab, so that one retires the session. A wait that ends with the request's context fails with `errFlareSolverrQueue`, which `finishScrape` does not count as a tracker failure and `scrapeMirror` does not treat as a lapsed login, since the tracker was never asked anything. Once `Close` has run the Scraper creates no more sessions, or a request still running at shutdown would replace one `Close` destroyed with one nothing destroys.
