# OpenAPI spec

`cmd/jacklet/public/openapi.yaml` documents the machine API Sonarr, Radarr and Prowlarr use, and a test holds it to the handlers in both directions. A change to an endpoint, a parameter or a response field changes the spec in the same commit. Read the entry for a rule before changing it.

## What the spec covers

- **API docs**: `cmd/jacklet/public/openapi.yaml` describes Jacklet's own HTTP surface (`/api/v2.0/indexers`, `/api/v2.0/indexers/{id}/results/torznab/api`, `/api/v2.0/indexers/{id}/results`) — it documents what Jacklet exposes, not the Torznab protocol itself (which has no OpenAPI spec of its own). `GET /docs` serves `cmd/jacklet/public/docs.html`, a Scalar API-reference page pointed at that spec via CDN script — no build step, no bundled JS in the repo. The script is pinned to an exact release with an `integrity` hash, so the page runs the code that was reviewed and a browser refuses anything else the CDN serves; moving to a newer release changes both together, the hash being the SHA-384 of that release's `dist/browser/standalone.js`, and the release has to read the OpenAPI version the spec declares. Both files are compiled in with `//go:embed public` and served from an `fs.Sub`, so the binary is genuinely self-contained and doesn't require its working directory to be the source tree. When adding or changing an endpoint (new query param, new response field, new route), update `openapi.yaml` in the same change so the docs don't silently drift from the actual handlers. The `/admin` panel is deliberately absent from it: the spec describes the machine API that Sonarr/Radarr/Prowlarr consume, and the panel serves HTML pages to a human, not a documented API surface.
- **The docs page's script and the spec lint's tools are pinned, to a release at least two weeks old where one serves**: the Scalar script runs in the docs page, and vacuum's image and action run against the checked-out repository, so each is pinned to an exact version: the newest published at least two weeks earlier, which gives a broken or compromised release time to be found and withdrawn before it runs. Where no release that old does what is needed, such as reading the OpenAPI version the spec declares or working in this CI, the oldest release that does is pinned instead, once its code has been read, and what it needs to do is written beside the pin.

## Ordering

- **`openapi.yaml` is ordered, like the Go structs**: `paths`, the `components` sections, the entries within each of them, and each schema's `properties` are sorted alphabetically. These are lookup tables — nobody reads `components/parameters` top to bottom — so alphabetical is what makes an entry findable, and it is where a newly added parameter belongs rather than appended at the end. Each schema's `required` is the sorted list of its own properties, which doubles as the check that catches a field added to a Go struct but left out of the spec: every field of `jackettIndexer`, `jackettCapability`, `searchResults`, `searchIndexer` and `jackettResult` is emitted unconditionally, so `required` and `properties` must match exactly.
- **…but an operation's `parameters:` list is grouped, not sorted**: Scalar renders parameters in document order, so that list is the order a human configuring Sonarr/Radarr reads. It is grouped by what a parameter is for — the indexer and the operation (`id`, `row`, `t`), the core search (`q`, `cat`), television (`season`, `ep`), the identifiers a tracker may be searched by directly, `extended`/`year`/`genre`, music, books, then paging (`limit`, `offset`) — and a new parameter goes into its group. Sorting it alphabetically scatters the pairs (`season` away from `ep`, `limit` away from `offset`) and opens the list with `album`, ahead of `q`. This is the same exemption `torznab.Channel` and `torznab.Item` take, where declaration order is the wire format; here it is the rendered format. The document's own top-level keys are exempt too, putting what applies to the whole document ahead of what it applies to: `openapi`, `info`, `servers`, `security`, `tags`, `paths`, `components`. So is the top-level `tags` list, which is the order Scalar's sidebar shows the operations' groups in.

## Style

The spec is read twice: as YAML by whoever edits it, and as the page Scalar renders at `/docs` for whoever configures a client. Where an established convention covers a choice — the OpenAPI specification itself, the rules vacuum's `recommended` ruleset checks (Spectral's `oas` rules, reimplemented in Go), yamllint's defaults — the spec follows it, so a reader who knows OpenAPI finds what they expect. The rest exist because YAML and the rendered page disagree about what a character means.

- **vacuum checks what it can see**: `.vacuum.yml` holds those rules, vacuum's `recommended` set and the project's own, and a finding names its rule and line, so they are not repeated here. A rule vacuum can check goes in `.vacuum.yml` rather than in this file, with a violation planted in `cmd/jacklet/testdata/openapi-violations.yaml` and an expectation in `scripts/check-vacuum-rules.sh`, which CI runs, since a rule that silently stops matching passes the spec as readily as one that holds. CI runs it through vacuum's action, the action and its image both pinned as the docs page's script is, with a minimum score of 100: the action fails only on errors and on the score, and every warning or info finding costs a point, so any of them fails the build, while a hint does not. `docs/development.md` has the command. What follows is what vacuum cannot see, and the reasons behind the choices it enforces without explaining.

### The document

- **`openapi` names the release the document is written against**: the newest patch of OpenAPI 3.2 at the time the spec was last edited, and an edit moves it to a newer patch if one has been published. A tool treats every patch of a minor release alike, so moving to a new patch changes the number and nothing else; a new minor release is adopted once Scalar and vacuum both read it.
- **A tag names the part of the API its operations belong to**: Scalar groups its sidebar by tag, so an operation with two would appear twice, and shows the tag's description as the group's introduction above its operations.
- **An `operationId` starts with a verb for what the operation does** (`listIndexers`, `downloadTorrent`): a client generator turns it into a method name, which reads as a call only when it starts with one. Nothing in Jackett's compatibility depends on it: clients address paths, not operations.

### Prose

- **A description is CommonMark**, which is what the specification defines every `description` field as and what Scalar renders, so the YAML text is source and the page is what a reader sees.
  - A literal a client sends or reads back is a code span: a parameter or field name, a value such as `all` or `t=caps`, a path, a template variable such as `.Query.IMDBID`, an environment variable, a content type, an example query. Double quotes are prose quotation, for words a person might say ("this tracker is down"), never a way to mark a value.
  - Code spans are the only Markdown used: no emphasis, lists, headings or links, so the source stays readable as plain text.
- **A `summary` is a short noun phrase in sentence case**, since Scalar shows it as the operation's title, and a response's description says what the body is rather than `OK`.
- **"id" is lowercase in prose** ("IMDb id", "row id", "indexer id"). The capitalized spellings are names Jackett's JSON uses, such as the `ID` and `TrackerId` keys, and appear only as code spans.
- **Components of one kind are described in one pattern**, so that a difference in wording reads as a difference in behavior: every external-id parameter says what it identifies and the template variable a definition reads it as, and every music or book parameter names the search it is for.

### Schemas

- **A body's example sits on the schema it illustrates**, as the `examples` array JSON Schema defines, rather than on the media type: vacuum asks for an example on each property of a body's schema whatever the media type carries, so an example kept on the media type would be written twice, and Scalar builds the example response it shows from the schemas. Error responses are the exception: they share `TorznabError` and `ErrorResponse` but not a payload, so each carries an `examples` map on its media type with the code and message that failure actually sends, as the schema's one example would show the wrong failure. A parameter's example is the OpenAPI `examples` map, each entry with a `summary`. Example data is invented, as everywhere in the project.
- **An error response documents the body in its endpoint's format**: a Torznab error document on the XML endpoint, the JSON error shape on the JSON ones, plain text on a download and on `/healthz`. A shared failure therefore has one response component per format, such as the unauthorized response's Torznab, JSON and plain-text variants, since the tests hold an operation's documented content types to the ones its handler sets, and one component listing every format would document types a handler never sends.
- **OpenAPI's own defaults are left out**: a parameter is not marked `required: false`, nor a query parameter `style: form` or `explode: true`. A `default` that documents the API's behavior, such as `offset`'s, is not one of these and stays.

### Key order

- **The keys of an object follow the specification's Fixed Fields table for it**, the one order a reader can look up rather than learn from this file. An entry is read through rather than looked up, so its keys are not alphabetical. For the objects the spec uses:
  - `info`: `title`, `description`, `contact`, `license`, `version`;
  - an operation: `tags`, `summary`, `description`, `operationId`, `parameters`, `responses`, `security`;
  - a parameter: `name`, `in`, `description`, `required`, `examples`, `style`, `explode`, `schema`;
  - a response: `description`, `content`, or a `$ref` alone;
  - a media type: `schema`, `examples`;
  - a security scheme: `type`, `description`, `name`, `in`;
  - a tag: `name`, `description`.
- **A schema, which has no such table, puts its type first**: `type` and the keywords that narrow it (`format`, `enum`, `default`), then `description` and `examples`, then `xml`, then its nested shape, `items` or `properties` and `required`.

### YAML

- **A description that spans lines is a `>` scalar**, never `>-` or `|`. Folding joins the lines with spaces, which is what lets prose wrap, and the trailing newline `>-` strips changes nothing on the page, so one indicator is used throughout.
- **A paragraph break is two blank lines**: in a `>` scalar one blank line becomes a single newline, which CommonMark reads as a soft break inside the same paragraph, and only two become the blank line that ends one.
- **Lines wrap at 80 columns**, yamllint's default, and a paragraph that is edited is refilled rather than left with a short line in its middle. A value that cannot be broken, such as a URL in an example, is the one thing that runs past it. A description that fits on its key's line within 80 columns is a plain scalar; one that does not, or that opens with a code span (a backtick cannot begin a plain YAML scalar) or contains `: `, is a `>` scalar.
- **Quotes appear only where YAML would otherwise read a different value**: a status code (`"200"` would be an integer key, where OpenAPI requires a string), a `$ref` (its `#` would start a comment), `version` (`1.0` would be a number), `"null"` in a type list, and in an example a string that looks like another type, such as an empty string (null), a number (`"2040"`) or a timestamp. Every other value is a plain or `>` scalar.
- **A list is a flow sequence only when it fits on one line** (`required: [ID, Name]`); a longer one is a block sequence, one `- ` item per line, never a flow sequence spread over several.
- **Blank lines separate the large entries**: one goes between the top-level keys, between the `components` sections, between paths and between schemas. The parameter and response components, a few lines each, run together.

## Testing

- **The spec is tested, not just described**: `pkg/torznab/openapi_test.go` parses `cmd/jacklet/public/openapi.yaml` (as a `yaml.Node`, so key order survives) and fails on drift — an undocumented struct field, a `required` list that no longer matches its properties, a component nothing references any more, a `$ref` that names nothing the document defines, a parameter documented on the XML search endpoint but not the JSON one, and either ordering rule broken. It also reaches past the spec into the handler, in both directions, since the rest of the tests compare the spec against itself: every documented query parameter is sent through `searchParamsFromQuery` and has to arrive in the `scraper.SearchParams` field named for it in `searchParamFields` — naming the field is what catches two parameters wired to each other's, where checking only that the value arrived somewhere would not — and every query parameter each operation's handler reads is read back out of the source and must be one the spec documents for that operation, as described below, so a name a handler starts reading cannot go undocumented either. The paths are held to the routes the same way: each documented API operation is sent to a mux `Torznab.Routes` built and must be routed by the route documented as it, not merely matched by a wildcard, and each pattern `Torznab.Routes` registers is read out of the source and must be documented, with a trailing-slash `{$}` form counted as its base path and the ignored Torznab action segment listed in `routeAliases`; a pattern that is not a literal, or any use of the mux other than registering a route on it, fails the test, since the routes registered through it could not be read, and a pattern that names no method fails it too, since it would answer every method, documented or not. The paths outside `/api/v2.0/` are the binary's own, and `cmd/jacklet/openapi_test.go` holds them to `run` the same way, against a running server and the mux its `http.Server` is handed, with the pages that are not API endpoints in its `undocumentedRoutes`. Both read the spec's operations and the registered patterns through `internal/routetest`, so a change to how a pattern is read, to which uses of a mux are refused, or to what each registered route is held to, applies to both; each test only finds its own mux and vouches for the uses of it that are not route registrations. Each operation's documented responses, query parameters and content types are held to its handler the same way, in both directions, by reading every function, method, variable and constant of its package the handler reaches, called or passed as a value, which is how what a shared helper does, such as the search path's failures or `searchParamsFromQuery`'s parameters, counts for each endpoint that calls it. The statuses are the `net/http` status constants in that code; the parameters are the string literals passed to a method of, or used to index, a value derived from the request's URL query, compared ignoring case and array brackets as the handlers look them up, with the API-key scheme's `apikey` counting as documented wherever the spec secures an operation; the content types are the literal `Content-Type` values it sets, and the media type net/http's `Error`, `NotFound` and `Redirect` set when a handler calls them (`text/plain`, `text/plain` with the 404 `NotFound` writes itself, and `text/html`), and a handler that also sets one computed at run time, as the download does from the tracker's answer, is not held to the documented one. A parameter the spec documents but a handler deliberately ignores, or one a handler reads but the spec deliberately leaves to another operation, is listed with its reason in `ignoredParameters` or `undocumentedParameters`, each entry of which must still be true. The values the spec's `enum` allows for the Torznab endpoint's `t` are held to the string cases of `ServeHTTP`'s switch on it, in both directions (`TestOpenAPIModesMatchTheHandler`), and a switch it cannot read, one not on a `Get("t")` of the request's query as `routetest.Source.IsQuery` reads it or with a case that is not a literal, fails the test; each value whose case calls `handleSearch` must also be one `canonicalSearchType` turns into a mode a definition knows. `cmd/jacklet/openapi_test.go` also holds every operation's documented security to a server started with an API key: a secured operation answers 401 without the key and something else with it, and one the spec opens with `security: []`, as `/healthz` is, never answers 401; the document's `{}` alternative stands for a server started without a key, so it leaves no operation open. Following a name reaches every declaration that has it, so the set can overstate what a handler writes; it misses a status only in code no name in the handler leads to, such as a function reached through a struct field a constructor fills. A name counts as another package's only in a file that imports it and where nothing local declares it, so a variable named like an import is still followed; a handler from another package is refused. An identifier handler is read as what it is declared as, so a local is read as the value it is declared with by the same rules as a handler written in its place, a value such as `&server{}` being served through its `ServeHTTP`, whatever package-level name it shares; a local declared without a single value of its own is refused. A handler that writes a body without a header answers 200 with no constant, so 200 counts as written when the code it reaches writes a body: a `Write`, `WriteString` or `Encode` call, one of `io`'s copies, `fmt`'s `Fprint` functions, or `net/http`'s `ServeContent` and `ServeFile` family. A documented 200 is held to that like any other status, so an endpoint that can only redirect or fail cannot go on documenting a body. The tests in `pkg/torznab/openapi_test.go` live in that package because it is the only one that can see both the spec and the response structs, which stay unexported. Adding a response field, a query parameter, a `t` value, a status a handler can answer, a content type it sets or a change to which operations need the key means updating the spec in the same change; the test says so rather than leaving it to a reviewer.
