# OpenAPI spec

`cmd/jacklet/public/openapi.yaml` documents the machine API Sonarr, Radarr and Prowlarr use, and a test holds it to the handlers in both directions. A change to an endpoint, a parameter or a response field changes the spec in the same commit. Read the entry for a rule before changing it.

## What the spec covers

- **API docs**: `cmd/jacklet/public/openapi.yaml` describes Jacklet's own HTTP surface (`/api/v2.0/indexers`, `/api/v2.0/indexers/{id}/results/torznab/api`, `/api/v2.0/indexers/{id}/results`) — it documents what Jacklet exposes, not the Torznab protocol itself (which has no OpenAPI spec of its own). `GET /docs` serves `cmd/jacklet/public/docs.html`, a Scalar API-reference page pointed at that spec via CDN script (`https://cdn.jsdelivr.net/npm/@scalar/api-reference`) — no build step, no bundled JS in the repo. Both files are compiled in with `//go:embed public` and served from an `fs.Sub`, so the binary is genuinely self-contained and doesn't require its working directory to be the source tree. When adding or changing an endpoint (new query param, new response field, new route), update `openapi.yaml` in the same change so the docs don't silently drift from the actual handlers. The `/admin` panel is deliberately absent from it: the spec describes the machine API that Sonarr/Radarr/Prowlarr consume, and the panel serves HTML pages to a human, not a documented API surface.

## Ordering

- **`openapi.yaml` is ordered, like the Go structs**: `paths`, the `components` sections, the entries within each of them, and each schema's `properties` are sorted alphabetically. These are lookup tables — nobody reads `components/parameters` top to bottom — so alphabetical is what makes an entry findable, and it is where a newly added parameter belongs rather than appended at the end. Each schema's `required` is the sorted list of its own properties, which doubles as the check that catches a field added to a Go struct but left out of the spec: every field of `jackettIndexer`, `jackettCapability`, `searchResults`, `searchIndexer` and `jackettResult` is emitted unconditionally, so `required` and `properties` must match exactly.
- **…but an operation's `parameters:` list is grouped, not sorted**: Scalar renders parameters in document order, so that list is the order a human configuring Sonarr/Radarr reads. It is grouped by what a parameter is for — the indexer and the operation (`id`, `row`, `t`), the core search (`q`, `cat`), television (`season`, `ep`), the identifiers a tracker may be searched by directly, `extended`/`year`/`genre`, music, books, then paging (`limit`, `offset`) — and a new parameter goes into its group. Sorting it alphabetically scatters the pairs (`season` away from `ep`, `limit` away from `offset`) and opens the list with `album`, ahead of `q`. This is the same exemption `torznab.Channel` and `torznab.Item` take, where declaration order is the wire format; here it is the rendered format. The document's own top-level keys are exempt too, keeping the conventional `openapi`/`info`/`servers`/`security`/`paths`/`components` reading order.

## Testing

- **The spec is tested, not just described**: `pkg/torznab/openapi_test.go` parses `cmd/jacklet/public/openapi.yaml` (as a `yaml.Node`, so key order survives) and fails on drift — an undocumented struct field, a `required` list that no longer matches its properties, a component nothing references any more, a `$ref` that names nothing the document defines, a parameter documented on the XML search endpoint but not the JSON one, and either ordering rule broken. It also reaches past the spec into the handler, in both directions, since the rest of the tests compare the spec against itself: every documented query parameter is sent through `searchParamsFromQuery` and has to arrive in the `scraper.SearchParams` field named for it in `searchParamFields` — naming the field is what catches two parameters wired to each other's, where checking only that the value arrived somewhere would not — and every query parameter each operation's handler reads is read back out of the source and must be one the spec documents for that operation, as described below, so a name a handler starts reading cannot go undocumented either. The paths are held to the routes the same way: each documented API operation is sent to a mux `Torznab.Routes` built and must be routed by the route documented as it, not merely matched by a wildcard, and each pattern `Torznab.Routes` registers is read out of the source and must be documented, with a trailing-slash `{$}` form counted as its base path and the ignored Torznab action segment listed in `routeAliases`; a pattern that is not a literal, or any use of the mux other than registering a route on it, fails the test, since the routes registered through it could not be read, and a pattern that names no method fails it too, since it would answer every method, documented or not. The paths outside `/api/v2.0/` are the binary's own, and `cmd/jacklet/openapi_test.go` holds them to `run` the same way, against a running server and the mux its `http.Server` is handed, with the pages that are not API endpoints in its `undocumentedRoutes`. Both read the spec's operations and the registered patterns through `internal/routetest`, so a change to how a pattern is read, to which uses of a mux are refused, or to what each registered route is held to, applies to both; each test only finds its own mux and vouches for the uses of it that are not route registrations. Each operation's documented responses, query parameters and content types are held to its handler the same way, in both directions, by reading every function, method, variable and constant of its package the handler reaches, called or passed as a value, which is how what a shared helper does, such as the search path's failures or `searchParamsFromQuery`'s parameters, counts for each endpoint that calls it. The statuses are the `net/http` status constants in that code; the parameters are the string literals passed to a method of, or used to index, a value derived from the request's URL query, compared ignoring case and array brackets as the handlers look them up, with the API-key scheme's `apikey` counting as documented wherever the spec secures an operation; the content types are the literal `Content-Type` values it sets, and a handler that also sets one computed at run time, as the download does from the tracker's answer, is not held to the documented one. A parameter the spec documents but a handler deliberately ignores, or one a handler reads but the spec deliberately leaves to another operation, is listed with its reason in `ignoredParameters` or `undocumentedParameters`, each entry of which must still be true. The values the spec's `enum` allows for the Torznab endpoint's `t` are held to the string cases of `ServeHTTP`'s switch on it, in both directions (`TestOpenAPIModesMatchTheHandler`), and a switch it cannot read, one not on a `Get("t")` of the request's query as `routetest.Source.IsQuery` reads it or with a case that is not a literal, fails the test; each value whose case calls `handleSearch` must also be one `canonicalSearchType` turns into a mode a definition knows. `cmd/jacklet/openapi_test.go` also holds every operation's documented security to a server started with an API key: a secured operation answers 401 without the key and something else with it, and one the spec opens with `security: []`, as `/healthz` is, never answers 401; the document's `{}` alternative stands for a server started without a key, so it leaves no operation open. Following a name reaches every declaration that has it, so the set can overstate what a handler writes; it misses a status only in code no name in the handler leads to, such as a function reached through a struct field a constructor fills. A name counts as another package's only in a file that imports it and where nothing local declares it, so a variable named like an import is still followed; a handler from another package is refused. An identifier handler is read as what it is declared as, so a local is read as the value it is declared with by the same rules as a handler written in its place, a value such as `&server{}` being served through its `ServeHTTP`, whatever package-level name it shares; a local declared without a single value of its own is refused. A handler that writes a body without a header answers 200 with no constant, so 200 counts as written when the code it reaches writes a body: a `Write`, `WriteString` or `Encode` call, one of `io`'s copies, `fmt`'s `Fprint` functions, or `net/http`'s `ServeContent` and `ServeFile` family. A documented 200 is held to that like any other status, so an endpoint that can only redirect or fail cannot go on documenting a body. The tests in `pkg/torznab/openapi_test.go` live in that package because it is the only one that can see both the spec and the response structs, which stay unexported. Adding a response field, a query parameter, a `t` value, a status a handler can answer, a content type it sets or a change to which operations need the key means updating the spec in the same change; the test says so rather than leaving it to a reviewer.
