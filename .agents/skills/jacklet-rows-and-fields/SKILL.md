# Rows and fields

A definition selects result rows from a tracker's answer and reads fields out of each, and Jacklet has to read them exactly as Jackett's CardigannIndexer does: a definition is written against Jackett, so a field read differently here is a release lost or mislabeled. Read the entry for a behavior before changing it.

## Selecting rows and fields

- **Row extraction is format-agnostic**: `resultRow` (`pkg/scraper/rows.go`) abstracts the three response formats a definition can declare, so `extractFields` is written once. A search path declaring `response: {type: json}` selects rows and fields by dotted key path instead of selector; `jsonScalar` renders a value as Jackett's Newtonsoft conversion does, a boolean as `True` or `False` and an array joined with commas, since definitions compare against those spellings, and formats numbers without scientific notation, since an id or byte count scraped as `1.2345e+04` is useless.
- **A `:root` selector reads the whole page, even from inside a row** (`rootSelector`, `htmlRow.scope`): Jackett strips the prefix and runs the rest from the topmost element, which is how a field or a `case` arm reads a page-wide banner or an info table outside every result row. goquery matches `:root` itself but returns only what lies inside the row, so without this such a field comes back empty and such an arm never matches. A `:root` arm under a field selector reaches the root the same way, from the element that field selected. `remove` is left as it is, as Jackett leaves it, and a whole-page check such as an error block already runs on the document, where `:root` needs no help.
- **Row and field selectors are templates**, as in Jackett: the row selector is rendered per search path (`scrapeMirror` hands `fetchRows` the result), which is how a definition narrows its rows to freeleech ones when a setting asks (`{{ if .Config.freeleech }}:has(...){{ else }}{{ end }}`), and a field's selector is rendered against the fields read before it, so a definition can pick a column by what an earlier field found. Download selectors are rendered the same way (`selectDownloadValue`).
- **A definition's CSS selectors are adapted to cascadia before they run** (`cssSelector`, `findIn`, `isMatch`, `pkg/scraper/selectors.go`): Jackett's definitions are written and tested against AngleSharp, which accepts what cascadia, goquery's engine, refuses, and a selector cascadia refuses matches nothing, silently, so a row selector written that way finds no row at all. An attribute value written unquoted, such as `[border=1]` or `[href^=details.php]`, and a `:contains` argument written unquoted are quoted, which changes nothing a selector cascadia already accepted means, since cascadia takes an unquoted value only when it is an identifier. `:scope` stands for the element the selector runs from, as in the `QuerySelector` Jackett runs from a row, and for the root element when it runs from the whole document, as a row selector or a login test does: cascadia has no `:scope`, so that element carries a marker attribute while the selector runs, and the selector names the attribute instead. Every place a definition's HTML selector is applied goes through them: rows and their `remove`, fields, case arms, a field's `remove`, the login's form, selector-keyed inputs, test and error blocks, and the `download` block's selectors. A selector is compiled by `compileSelector`, which also supports what cascadia cannot: a group alternative ending in a relative `:has`, one whose argument starts with `~`, `+` or `>`, such as `div.post:has(~ div.entry a.download)`, which AngleSharp accepts (`relativeHas`, `trailingRelativeHas`). The element is tested against the rest of the alternative, any element when nothing precedes the `:has` but a combinator, then marked with another attribute while the argument runs from it, below its parent for a sibling combinator. The whole group compiles into one matcher, so what it selects stays in document order whichever alternative selects it, which a definition pairing each post with the entry after it (`after: 1`) depends on. A relative `:has` anywhere but the end of an alternative is not supported and matches nothing, as does a group with any alternative that cannot be compiled.
- **A field selector the row itself matches selects the row** (`htmlRow.selection`): Jackett resolves a field as `Dom.Matches(selector) ? Dom : QuerySelector(Dom, selector)`, so a definition whose rows are links reads each link's own `href` by naming the link, and one whose rows are a single element reads that element's text or attributes. Searching only inside the row finds nothing there, and since such fields are usually required, every row is dropped and the indexer returns no results at all. The row is tested first, as Jackett tests it, so where both the row and a descendant would match, the row wins. A `:root` selector skips the test, since Jackett's own match sees the prefix it cannot evaluate. A field's `case` arms see the same selection, since `narrow` resolves it through `selection` too.
- **A field reads only its selector's first match** (`htmlRow.selection`, `xmlRow.lookup`, `xmlRow.narrow`): Jackett resolves a field with `QuerySelector`, which returns the first element in document order, so a definition writes a selector that is unique only up to that. goquery's `Text` joins every match instead, which turns a title selected by `a` in a row of several links into all their text run together. Both row types narrow the selection to the first match before reading text or an attribute.
- **A required field that doesn't match drops the row**: `extractFields` returns `ok=false` unless a field is optional (`NamedField.isOptional`), matching Cardigann rather than storing a row with a hole in it. A field is optional when the definition declares it so, and always when it is one Jackett treats as optional whatever the definition says (`alwaysOptionalFields`: the external ids, `poster`, `genre` and `description`), which a tracker shows for some releases and not others. Be careful changing this: it silently changes how many results a definition yields.
- **A field whose own template names a variable never set fails** (`renderFieldTemplate`, `readField`, `applyFieldFilters`), as Jackett's dictionary lookup throws and fails the field: a required one drops the row, and an optional one comes back empty without its default, which Jackett skips once the field has thrown. The field's own templates are its selector, the case value that matched (an unmatched arm's is never rendered), its text and its filters' arguments; the variable may be a field declared later or not at all, or a setting the definition does not declare. Only a missing variable fails the field: a template failing for another reason is left as written, as `renderTemplate` leaves it. Jacklet builds `.Result` afresh for each row, so a field named before it is read is always missing, where Jackett's one dictionary per search hands the second row on the first row's value. A login's selector input fails the login the same way, optional or not, as in Jackett.
- **A field key is a name and modifiers** (`NamedField.Modifiers`, `FieldList.UnmarshalYAML`), split at `|` as Jackett splits it, and the name alone is what the row and `.Result` know the field by, so `categorydesc|append` is read as `categorydesc`. `|optional` makes the field optional, like its `optional` key. `|append` adds a `title` or `description` to the one an earlier field of that name read (`NamedField.appends`, `setField`), `.Result` included, and is ignored on any other field, which replaces as usual; an empty appended value leaves the earlier one as it was, in `.Result` too. That last part is a deliberate difference: Jackett blanks `.Result.title` after an empty optional append while the release keeps its title, so a later template reading it sees nothing, which Jacklet, keeping one map for both, does not reproduce: such a template sees the title read before the append. Jackett looks its always-optional fields up by the whole key, so a field carrying a modifier is optional only when it says so (`NamedField.isOptional`). The deprecated `|noappend` is not modeled, so a field carrying it is read as a plain field and replaces an earlier one of its name.
- **An optional field that comes back empty takes its `default`** (`Field.Default`), as in Jackett: the default is a template rendered against the fields read before it, the common case being a title built from another field (`default: "{{ .Result.title_default }}"`), and without it that row has no title and is dropped. It is rendered strictly and without the field's filters, so a default naming a field that does not exist leaves the field empty, as Jackett's failed lookup does, and a required field never takes one. An optional field that does not match at all gets no filters either, since filters run over a value and there is none; Jackett returns nothing for it before they would run.

## Case arms

- **A field's `case` arms are tested against what its selector selects** (`resultRow.narrow`, `resolveCase`): Jackett resolves the field's selection once (the row itself, a `:root` selection, or the first match) and tests each arm as `selection.Matches(arm) || selection.QuerySelector(arm) != null`, which is what `narrow` followed by `matches` reproduces. Gluing the field selector and the arm into one selector string instead breaks in two ways real definitions hit: a selector list `A, B` glued to an arm reads as "A, or (B arm)", so the first alternative decides every row, and an arm describing the selected element itself, such as `td:not([title])` under `td`, can never match because the glued selector only looks below it. A field with no selector of its own tests its arms against the whole row.
- **A `case` arm's value is a template** (`extractFields`): Jackett renders the matched arm's value with `applyGoTemplateText`, in HTML and JSON alike, and definitions depend on it. The common flag pattern, arms valued `"{{ .True }}"` and `"{{ .False }}"`, yields Cardigann's booleans only once rendered; kept as text, `{{ .False }}` is a non-empty string that every template reads as true.
- **A JSON answer's rows are shaped by the rows block** (`jsonRows`, `splitJSONRow`), as Jackett shapes them: `attribute` narrows each element of the rows array to an object inside it, `multiple` makes each entry of that object or array a row of its own (a movie's several torrents), and a field selector starting with `..` reads the element the row came from (`jsonRow.parent`), which is how such a row reads its movie's title. `count` is read from the whole answer first (`jsonRowCount`), and an answer counting fewer than one result has none, whatever rows it carries. A row selector naming a key the answer lacks fails the search, as in Jackett, so an error answer of another shape is reported rather than read as no results, unless the definition sets `missingAttributeEqualsNoResults`; a row selector addressing `null` is no results, and an element lacking `attribute` yields no row where Jackett fails the search.
- **A JSON selector carries Jackett's filters** (`jsonSelect`): the path before the first `:` addresses a value, and each `:has(...)`, `:not(...)` or `:contains(...)` after it must hold for that value, or nothing is selected. On a row selector they keep only the elements they hold for, before `attribute` and `multiple` shape them, which is how the `-api` definitions offer freeleech-only results (`:not(promotion_info.down_multiplier:contains(1)):not(...:contains(.))`). `jsonFilters` reads them as Jackett's pattern does, not by balancing parentheses: an argument runs to the first `)` that ends the selector or precedes the next `:`, which is what lets a filter's argument be a selector with filters of its own. `:contains` tests the value's text as written, quotes included, and an object's or array's JSON.
- **A JSON `case` arm is a value, not a key** (`jsonRow.matches`): Jackett resolves a JSON field's arms by comparing each with the value the field selected (`value.Equals(arm)`), so API definitions write arms such as `False`/`True` or `0%`/`50%`. Read as key paths, none of them matches, and since the usual `False`/`True` flag is a required field with no `*` arm, every row of such an indexer is dropped. The comparison relies on `jsonScalar` spelling a boolean as `True`/`False`, which is why its rendering follows .NET's rather than Go's.

## XML

- **`response: {type: xml}` has its own parser, and cannot reuse goquery** (`pkg/scraper/xml.go`, in practice always an RSS feed). The definitions keep writing CSS selectors, but an HTML parser cannot serve them: it lowercases element names, so a definition's `pubDate` never matches `<pubDate>`; and `<link>` is a void element in HTML, so the text of an RSS `<link>https://…</link>` is parsed *outside* the element and comes back empty — which is the details URL for many of them. Jackett reaches for a separate XML parser for the same reason. So `parseXML` builds a tree with `encoding/xml` and `selectXML` implements the selector subset those definitions actually use: element names, `[attr]` and `[attr=value]` predicates, and the descendant and child combinators, all matched **case-sensitively** as XML defines them. A selector outside the subset matches nothing rather than pretending. Two details that are easy to undo by accident: the decoder is given a pass-through `CharsetReader`, because `fetch` has already decoded the body to UTF-8 and a feed still declaring `windows-1251` would otherwise be refused; and a namespaced `<torznab:attr>` is stored under its local name, which is what `[name=seeders]` selects against.

## From fields to a torrent

- **A tracker's categories come from both forms of caps, under Jackett's names** (`Caps.UnmarshalYAML`, `standardCategoryIDs`): Cardigann's older `caps.categories` map, a site id to a standard name, is folded into `CategoryMappings` ahead of the `categorymappings` list, in the order written, as Jackett adds both to one table, so caps, row mapping and the site ids a search sends all read it. A name matches only as Jackett spells it, exactly: its console categories are `Console/XBox`, `Console/XBox 360` and so on, with a capital B, and "tidying" the table's spelling silently sends every mapping written that way to the default category.
- **A described mapping makes a custom category** (`CategoryMapping.customCategoryID`, `CustomCategories`), as Jackett makes one, so a client can ask for one tracker category by itself: it is named by the `desc` and numbered past 100000 by the tracker's id when that parses as a 32-bit integer, and otherwise by the first two bytes of the id's SHA-1, read little-endian. Jackett's numbering is reproduced exactly, because a client configured against Jackett saved those numbers; a counter would also renumber on every edit of the definition. A mapping that names no standard category makes none, as Jackett skips the whole mapping. A search for a custom number asks the tracker for the category that made it (`siteCategoryIDs`), and a row in that category carries the number, so the stored results answer it too.
- **A row is filed under every category its fields map to** (`mapCategories`, `mapCategoryDescs`, `Torrent.Categories`), as Jackett files it: its `category` field is matched against the mappings' ids and its `categorydesc` field against their `desc`, both as text with case ignored, and every standard category a matching mapping names is kept, once each, in the order the mappings are written, each followed by the mapping's custom category when it has a `desc`, so a tracker category mapped to `Movies/HD` and `Movies/UHD` is served under both. Only those two fields are read: a definition's helper field such as `category_id` reaches the row through `{{ .Result.category_id }}` in its `category` field, as in Jackett. A mapping naming no standard category is skipped, and a row mapping to none is filed under none, as in Jackett, which keeps such a release for its interactive search and drops it from everything else: the Torznab feed asks the store to leave it out (`Query.NeedsCategory`), while the JSON results endpoint, Jackett's interactive search, and the panel show it, with an empty category list. Leaving it out of the query rather than off the page keeps the feed's paging and total right, and a category filter still matches it, as Jackett's does.
- **`torrentFrom` maps every Cardigann field Jackett does, and parses them the way Jackett does.** The numeric fields go through `coerceLong`/`coerceDouble`/`parseSize`, which mirror `ParseUtil`: they keep the digits and treat both `,` and `.` as digit grouping. This leniency is the whole point — a tracker rendering "1,234" seeders or a "0,5" volume factor is ordinary, and a strict `strconv` parse turns the first into zero (a release that looks dead and gets discarded) and the second into the default 1 (a half-leech release advertised as fully counted). `coercePeerCount` additionally zeroes a count at or above 5,000,000, which is Jackett's guard for placeholder columns that parse into an enormous number. The `date` field is resolved with `parseUnknownTimeValue`, the same heuristics as the `fuzzytime` filter, because Jackett applies `FromUnknown` here and a definition is therefore not required to declare a date filter at all.
- **A size with no unit is a byte count**: many definitions select a site's raw size field rather than a human-readable one, so `parseSize` treats a bare number as bytes. An unrecognized *unit* is still an error, so a mis-parsed size is never mistaken for a real one.
- **External ids are stored as digits, and the poster attribute is called `coverurl`.** `extractDigits` mirrors `ParseUtil.GetLongFromString`, so a field holding `tt1234567` or `tmdb/955` stores just the number, which is what Jackett puts in the attribute. `genre` is normalized by `parseGenres` — split on the same delimiters `validate` uses, `_` becomes a space, repeats dropped, joined with ", ". Note two names that do not match their Cardigann field: the `poster` field is served as the **`coverurl`** attribute, and `imdb`/`imdbid` are one field in Jackett, so `torrentFrom` reads both spellings and stores the digits. The feed then emits the id **twice** — `imdb` as the bare number zero-padded to seven (`imdbNumber`) and `imdbid` as the canonical `tt` form (`IMDBID`), which is also what the JSON endpoint reports — because clients look for one name or the other. Neither is emitted when nothing was scraped, deliberately unlike Jackett, which emits `tt0000000` for a row whose imdb field was empty and invites a client to match on it. When adding a media field, it has to land in all four places — `scraper.Torrent`, the schema, `torrentColumns`/`scanTorrent`/`upsertSQL`/`upsertArgs`, and `torznab.attributes` — and the round-trip test in `pkg/database/metadata_test.go` is what catches a field wired into three of them.
