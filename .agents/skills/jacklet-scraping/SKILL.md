# Scraping

`pkg/scraper` fetches each tracker's search pages as its definition describes and hands the results to a `Sink`. One `Scraper` serves every request, and the tracker on the other end is a third-party site that may be slow, broken or hostile, which shapes most of what follows. Read the entry for a behavior before changing it.

## The Scraper and its results

- **A `Scraper` needs no storage, and persists only through a `Sink`**: `Scrape` returns the torrents a search found, so a program that keeps its own results passes no `Options.Sink` and stores nothing anywhere. `cmd/jacklet` sets `Options.Sink` to the `database.Store`, which is also what `torznab` and `admin` read, so a scraper whose sink does not write where the handlers' `Catalog` reads refreshes rows those handlers never see — `torznab.New` says so. Three rules hold it together. **The leader persists, once**: an identical search made while one is running follows it (`scrapeFlight`) instead of repeating it, and the flight carries the leader's torrents to every follower, so each caller gets results while only the leader calls the sink; the shared slice is read-only. **A failing sink does not fail the scrape**: it is logged and the torrents are still returned, since the tracker answered and a store outage should cost persistence, not the result. **A skipped search says so** — `ErrThrottled` when the tracker is backing off or the search repeats one completed within `minScrapeInterval`, never an empty slice that reads as "the tracker has nothing" — and `torznab` and `admin` read it as "answer from the store", not as a failure. The sink is called once per scraped page, not once per scrape, so a later path failing keeps the earlier pages. A scraper with no sink is not an error, since a program may keep the returned torrents itself, but `torznab.New` and `admin.New` log a warning when `Scraper.HasSink` is false, because a handler over a store can then never see a scrape's results. `docs/embedding.md` is the guide for a program importing these packages, and the wiring it shows is `Example` in `pkg/jacklet/example_test.go`, which the tests compile and run — change one with the other, and a new page in `docs/` is either rendered as a manual page or named in `skipped` in `packaging/mkman/adapt.go`, which is where an embedding guide is listed.
- **One shared, long-lived `Scraper`**: `jacklet.New`, which `main.go` calls, constructs exactly one `scraper.Scraper` and hands it to both the Torznab API and the admin panel — don't construct a fresh `Scraper` per request. It's safe for concurrent use and holds state that must persist across requests to be useful: the HTTP client's cookie jar (session cookies from one request are available to the next), the cached FlareSolverr sessions (`flareSolverrSession`, one per tracker, reused instead of re-solving a challenge every search), and per-tracker rate-limit/backoff bookkeeping (`scrapeState`, `planScrape`/`finishScrape`); a follower is counted on its flight (`scrapeFlight.followers`, reported by the debug log and awaited by the test that needs a follower to have joined before the leader is released). `main.go` calls `scrpr.Close(ctx)` on graceful shutdown (`SIGINT`/`SIGTERM` via `signal.NotifyContext`) to destroy that FlareSolverr session rather than leaking it server-side.
- **Rate limiting with backoff**: a request for the same indexer within `minScrapeInterval` (5s) is not re-scraped: `Scrape` returns `ErrThrottled` and the handler answers from whatever's already in the database. A failed scrape additionally backs off exponentially (`minScrapeInterval * 2^failures`, capped at `maxScrapeBackoff` = 10m) so a persistently broken tracker isn't hit every 5s forever; a success resets the failure count.
- **A definition's `requestDelay` spaces every request it makes** (`Tracker.RequestDelay`, `paceRequest`), as Jackett's web client does: the seconds it names are left between the tracker's answer to one request and the sending of the next, so a slow answer does not use up the gap. It covers each page a search fetches, a login's requests, a download block's pages and the torrent file, whether the page is fetched directly or through FlareSolverr, since all of them go through `fetch` or `fetchTorrent`. Concurrent requests take turns, one in flight at a time (`requestTurn`), which Jackett does not do; without it, searches running side by side would send a tracker that allows one request every two seconds several at once, and an answer slower than the gap would let the next request go straight after it. It is separate from `minScrapeSpacing`, which spaces whole searches. A request waiting its turn gives up with its caller's context and gives the turn back, and its error wraps `errRequestQueue`, which `isQueueWait` reads as the FlareSolverr queue's is read: the tracker was asked nothing, so the scrape's failure neither counts against it nor drops its login. A queue wait never replaces a failure the scrape already saw (`trackerError`), so a hung mirror followed by a failover that gives up waiting still counts against the tracker. A delay is read as at most `maxRequestGap`, so an absurd value converts to a duration the same way on every platform; a gap that long already outlasts any search. The turns live in `Scraper.requestTurns`, apart from `scrapeState`, whose entry is what marks a tracker as searched, since a download is paced too. A redirect the HTTP client follows within one request is not spaced, where Jackett's own redirect following waits before each hop.
- **A panicking scrape is recorded as a failure**: extraction runs over whatever a tracker serves, so `Scrape` recovers a panic into its own error return and the tracker fails the way an unreachable one does. That `defer` is registered after `finishScrape`'s, so it runs before it — the recovered failure has to be in the named return by the time the bookkeeping reads it, or the scrape is filed as a success, resetting the tracker's backoff, arming the de-duplication window for results that were never stored, and handing followers of the same search a nil error. The stack is logged rather than served, and recovery contains a panic rather than excusing one.

## Fetching

- **A definition's `encoding:` applies to the request, not just the response** (except a POST through FlareSolverr, which reads the form as UTF-8, replacing every byte that is not, and submits a new UTF-8 form, so a legacy-encoded search term arrives as replacement characters and a field named `submit` is dropped; `warnFlareSolverrForm` says so once per tracker, and a GET is unaffected because its query string reaches the browser as it is): `encodeForm` transcodes the submitted form into the tracker's character set before percent-encoding it, and sets the charset on the POST `Content-Type`. A windows-1251 tracker sent UTF-8 search terms does not fail — it reads the query as mojibake and silently returns its default listing, so this is pinned by asserting the bytes actually sent (`TestScraperEncodesFormInTrackerCharset`), not by whether a scrape succeeds.
- **Outbound requests honor the standard proxy variables**: the FlareSolverr client leaves `Transport` nil, and the tracker clients — searches, logins and downloads — share `certificatePins`, whose transports are all clones of Go's default, so `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` (an `http`, `https` or `socks5` URL, credentials in its userinfo) apply to every request. That is the whole implementation, so there is no `JACKLET_*` setting for it and it is read once per process. Giving a client a transport of its own must carry `Proxy: http.ProxyFromEnvironment` over, or proxying stops with no other symptom; `TestScraperSendsRequestsThroughEnvironmentProxy` is what fails, and it re-runs the test binary because the variables are cached on the first request. FlareSolverr's browser ignores them and takes `PROXY_URL` on the FlareSolverr side, which FlareSolverr applies to a session opened with `sessions.create`, as Jacklet opens each of its own. A session FlareSolverr creates implicitly, under the name a request carries, gets no proxy; that happens only when `verifyFlareSolverrSession` could not reach FlareSolverr and kept a session a restarted FlareSolverr no longer holds. An operator using both should name the same proxy in each, since a download is fetched by Jacklet with the browser's clearance, which is usually bound to the address that earned it, and should list the FlareSolverr host in `NO_PROXY`. The Windows service's registry settings carry only `JACKLET_*` settings, so `jacklet service config` cannot set a proxy.
- **A definition's pinned certificates are trusted on its own hosts only** (`Tracker.Certificates`, `certificatePins`), as Jackett trusts them: a tracker whose certificate has expired or is self-signed lists its SHA-1 fingerprint, and a connection whose chain fails the standard verification is accepted when its leaf is pinned for the host it was made to. The pins are registered for the hosts in the definition's links and legacy links when it is first scraped or downloaded from, so a definition cannot weaken TLS for a host it does not name, and a pin is consulted only after the standard verification fails, so it can never reject a connection. A host with no pins uses the base transport, verified exactly as Go verifies; a pinned host gets a transport of its own because the check has to know which host a connection was meant for, and the TLS connection state leaves the name empty for an IP address, which would otherwise skip the hostname check altogether. The check uses the name the handshake asked for when there is one and the transport's host only when there is not, because the same transport makes its handshake with an `https://` proxy, whose certificate is for the proxy's name and whose handshake the tracker's pins must not cover; an `https://` proxy addressed by IP in front of a pinned tracker is the one case this cannot tell apart. Pins are only added, as in Jackett, so one stays trusted until restart after its definition drops it. FlareSolverr's browser does its own TLS, so pins do nothing for a tracker reached through it.
- **A search does not follow redirects unless its path says to** (`SearchPath.FollowRedirect`): `fetch` picks `noRedirectClient` by default and `httpClient` when the path sets `followredirect: true`. This is Cardigann's default and the reason for it is worth keeping in mind — a tracker whose session has lapsed answers a search by redirecting to its login page, and following that scrapes the login page as if it were results, turning a lapsed session into a silent "no matches". Whatever the 3xx carries is parsed instead, which for a bare redirect is nothing. The two clients **share one cookie jar**, so a session established by the login flow is still sent; a second `http.Client` that quietly had its own jar would log every scrape out.
  - Note the name is used twice in the Cardigann format. Inside a search path it is this. At the **top level** of a definition it is a different setting, which in Jackett rewrites the configured site URL when a login test is redirected elsewhere; Jacklet does not implement that, since it answers a moved site with mirror failover rather than by editing an operator's configuration.
- **A tracker address never leaves the scraper whole** (`pkg/scraper/redact.go`: `redactAddresses`, `redactingHandler`, `redactedPath`): many trackers carry the passkey in a query string, and a failed request, or a link that does not parse, is reported by Go with the whole URL. Every error `Scrape` and `Download` return has the query string and fragment of each address it names replaced with a note saying so, and the scraper wraps the logger it is handed so every error a log line carries is redacted the same way, wherever it is logged. A search path is logged with each literal value in its query and fragment replaced, keeping its keys and template actions, and with any run elsewhere that looks like a passkey (a single run of at least `minTokenLength` letters and digits, with both among it, so a dated segment or an id list joined by `-` or `_` is kept) replaced too, since a definition may write its passkey there itself. `Scrape` redacts after a panic is recovered and before `finishScrape` records the failure, so followers and the tracker's status see the redacted error too. A redacted error answers `errors.Is` for everything it wrapped but does not unwrap, so `errors.As` finds nothing in it: the chain it replaces still holds the unredacted `*url.Error`. A new exported method that returns a fetch's error redacts it on the way out, as these two do.
- **An empty response body is an answer, not an outage**: `charset.NewReader` reports an empty read as `io.EOF`, which `fetch` turns into an empty string rather than passing on. Left as an error it becomes "all links unreachable" — mirror failover, and a 502 to a client that should have been told "no results". An unfollowed redirect is the common case, but a tracker answering 204, or 200 with nothing, is the same thing.
- **A response is bounded, because nothing else bounds it** (`defaultMaxResponseBytes`, 32 MiB, held on the `Scraper` so a test can lower it): the HTTP client's timeout bounds how *long* a response may take, not how large it may be, and `fetch` reads the whole body into memory and then builds a document tree on top of it. The aggregate indexer makes that concurrent across as many trackers as `maxConcurrentScrapes` allows. The same cap covers the FlareSolverr reply, which carries the rendered page as JSON and is the same exposure by another route. Exceeding it **fails the scrape** rather than truncating: half a document parses into plausible-looking nonsense, which is worse than an error that says what happened. A real listing page is tens of kilobytes, so the cap is invisible in normal use — raise it rather than removing it if some tracker ever needs more.
- **Link fallback**: `Scrape` tries `Links` then `LegacyLinks` in order (`candidateBaseURLs`), stopping at the first one where at least one search path's fetch succeeds. A mirror that connects but returns zero matching rows is not a failure — don't reinterpret "no results" as "try the next mirror." A row's relative download/details URLs are resolved against **the search page that served it** (`storeRows` threads `searchURL` into `torrentFrom`), as a browser resolves them: a definition whose search path sits in a subdirectory, such as `forum/tracker.php`, carries row links relative to that directory, and resolving them against the site root addresses a page that does not exist — never against `def.Links[0]`, which points at the dead primary after a failover and panics outright on a definition that declares only `legacylinks`.
- **A search path is a template, resolved as an address** (`searchPathURL`): its rendered path is parsed and resolved against the mirror, as Jackett resolves it against the site link, so a `?` the path carries starts the query string the inputs are added to, and an absolute address replaces the mirror's. A path that fails to build fails that path, and the login stands, since the tracker was not asked anything.
- **A search path is a GET unless it says `post`** (`SearchPath.httpMethod`), as in Jackett: a GET carries its inputs in the query string where a POST sends them as a form. The fetch and the repeated-request skip both read it, so they cannot disagree about which requests are GETs.
- **An input that renders empty is not sent** (`pathForm`), as in Jackett: a value that is empty or blank once rendered is left out of the form unless the definition sets `search.allowEmptyInputs`. Definitions are written for it — `q: "{{ .Keywords }}"` on a browse, or a sort setting left at nothing — and a tracker may read an empty parameter as a search for nothing, or refuse it. `$raw` is never dropped this way, and neither are a login's or a download's inputs, which Jackett sends as they are.
- **A repeated search request is asked once** (`scrapeMirror`), as in Jackett: a path whose GET, address and form alike, repeats one already made on the same mirror is skipped, whatever made the two paths build it, since the second request would fetch the same page and hand the Sink every row again.
- **An older definition's single `search.path` is one more path** (`Search.UnmarshalYAML`): Jackett adds it after any `paths` the definition lists, inheriting the search's inputs, and Jacklet folds it into `Paths` the same way when the definition is decoded, so nothing downstream sees the singular form. Without it such a definition has no path, and every search of it fails.
- **A search path may declare the categories it serves**: `SearchPath.selectCategories` skips a path with no category in common with the search, and narrows that path's own `.Categories` to the ones they share — so a definition keeping movies on one page and music on another fetches one page per search rather than both. A path declaring none always runs, over all of them. Two things follow from it:
  - **A search naming no category falls back to `DefaultCategoryIDs`**, the mappings marked `default: true`, exactly as Jackett does. Without that fallback an unfiltered search would share no category with any declared path and fetch nothing at all. Most definitions mark none, and then `.Categories` stays empty — which is what a definition's `{{ if .Categories }}...{{ else }}` branch is written for, so don't "fix" the empty case by substituting every category.
  - **Every path being skipped is not a failure.** `scrapeMirror` reports such a mirror as reachable: it was never asked anything, so failing over would ask the next mirror the same question and skip the same paths, and reporting the tracker as down would turn "this search matches no page of this site" into an error the client sees.
  - One Jackett quirk is replicated rather than improved on: a *negated* path (`categories: ["!", 401]`) that does run gets an **empty** `.Categories`, because Jackett computes the same intersection in both branches and the one it just found empty stays empty. A definition using the negated form would have been written against Jackett's reading, and matching the quirk is what lets it work here unmodified — which is the compatibility the project exists for.

## Logging in and configuration

- **Login**: `pkg/scraper/login.go` implements Cardigann's `form`/`post`/`get`/`cookie` methods, adopting hidden form fields (CSRF tokens) from the login page. A form login uses the form its definition names, and the page's first `form` when it names none, as Jackett does, and posts to that form's `action`; it adopts only what a browser would submit (`isSubmitted`), so a disabled input, or a checkbox or radio button left unchecked, is not sent. A post or form login first loads the cookies its definition declares into the jar (`Login.Cookies`, `setLoginCookies`), as Jackett sends them with its login requests, whatever they are; `JAVA=OK`, for example, gets past a tracker's check that the browser runs scripts. With `selectors: true`, a form login's input keys are CSS selectors for the inputs they fill (`inputsBySelector`), each submitted under the name of the input it selects, for a page whose input names change while their ids or placeholders do not; a selector that selects nothing, or an unnamed input, fails the login, and the check for blank credentials runs again on the resolved names. A form login's `selectorinputs` read further values off the whole login page, each as a field reads its row (`readSelectorInputs`), for a token the page keeps in a script or outside the form; a required one that matches nothing fails the login before anything is sent, and an optional one is left out. Credentials come from the definition's own `username`/`password` settings via `JACKLET_CONFIG_DIR`, the same overrides every other setting is read from. A successful login is trusted for `loginValidity` (30m) rather than re-tested every scrape; a failed fetch invalidates it so the next scrape re-authenticates. A `captcha:` block is reported as `ErrCaptchaRequired` rather than attempted.
- **A nil config value is an empty string**: `mergedConfig` maps a setting with no default, and an override written as a bare `password:` with no value, to `""`. Formatting a nil `any` with `%v` yields the literal text `"<nil>"`, which would otherwise be sent to a tracker as a password.
- **A renamed tracker answers to its old ids** (`Tracker.Replaces`, `DefinitionStore.Find`, `TrackerOverrides`), as Jackett's `replaces` makes it: `Find` falls back to the definition that lists an id under `replaces` when no definition has that id itself, so a client set up with the old id keeps working (Jackett looks an old id up first, even over a definition that has it, where Jacklet lets that definition keep its id); each request by an old id logs a warning naming the new one, as Jackett's does, so the operator can move the client over. A tracker with no saved settings of its own uses those saved under the first id it replaces that has any. Every reader of a tracker's settings goes through `TrackerOverrides` (a search's `.Config`, the FlareSolverr opt-in, the panel's page and its save), so all of them agree; saving in the panel writes under the tracker's own id, carrying a masked secret over, and then removes the files saved under the ids it replaces, so the settings move as Jackett moves them. The removal is what keeps an empty save standing: saving nothing deletes the tracker's own file, and an old file left beside it would stand in again. Jackett moves the old file at startup instead; Jacklet reads it where it is until that save and changes nothing in the configuration directory before it. An id another loaded definition still has stays that definition's, its settings included, so `DefinitionStore` leaves it out of the `replaces` of every copy it hands out (`handOut`), and nothing reads or removes its file on the renamed tracker's behalf. Settings under an old id that cannot be read are not carried over, and the panel's save keeps their file for the operator to repair. An old id is a filename in the configuration directory, so `ConfigStore.Overrides` refuses one that would name a file outside it, as `Save` does. `TrackerOverrides` passes over such an id rather than failing on it, since it cannot hold saved settings, so the ids listed after it are still read. Rows stored under an old id are not served under the new one, since the store is a cache a search refills.
- **Config overrides**: `JACKLET_CONFIG_DIR/<tracker-id>.yml` (default dir `config`, missing file is not an error) is a flat `setting-name: value` YAML map layered over a definition's own `settings:` defaults — see `scraper.ConfigStore` in `pkg/scraper/config.go`, the file-backed implementation of `scraper.ConfigSource` (all the scraper reads: `Overrides`) and of `admin.Config` (what the panel edits through: that plus `Enabled`, `Location` and `Save`), so a program embedding either can keep settings elsewhere; the scraper and the panel must be given the same place, or a saved change never reaches a scrape, and `configtest.Run` (`pkg/scraper/configtest` for a `ConfigSource`, `pkg/admin/configtest` for a `Config`, which runs the first through `Save`) holds an implementation to what they rely on, run against `ConfigStore` and the panel tests' in-memory `fakeConfig`, and the panel shows `Location` next to the save button and names no directory itself. Writing overrides may change credentials, so a caller that holds a `Scraper` must follow `ConfigStore.Save` with `Scraper.InvalidateLogin`. This is the only way to change a `.Config.*` value Jacklet currently has; there's no runtime/API-driven config mechanism.

## Loading definitions

- **Definitions are cached, not re-parsed per request**: `DefinitionStore` (`pkg/scraper/store.go`) holds the parsed definitions and re-reads a file only when its size or modification time changes, so a file added, edited, or removed still takes effect on the next lookup without a restart. `main.go` builds one and passes it through `jacklet.New` to both the API and the panel, and every handler goes through it. Caching is what makes a Jackett-sized directory viable: parsing every file on every request costs time and allocations in proportion to the directory, and the project exists to serve directories of several hundred definitions. `Find` copies only the definition it matched rather than materializing the whole directory, since it runs on every search. The copy is deep (`cloneTracker`), so a caller editing what it was handed cannot change what the next caller sees; `TestCloneTracker` fills every field of a `Tracker` by reflection and fails on any slice, map or pointer the copy still shares, so a field added to the definition fails it until `cloneTracker` copies it too.
- **A broken edit doesn't take an indexer off the air**: a definition that parsed before and fails to parse now keeps serving its last good version, with the failure reported alongside it in `Trackers`. Without this, saving a syntax error mid-edit would 404 a live indexer until it was noticed.
- **Broken definitions are surfaced, not just skipped**: `DefinitionStore.Trackers` returns `(trackers, []DefinitionError, error)` — a file that fails to read/parse is skipped and reported in the `DefinitionError` slice rather than aborting the whole directory load. `DefinitionStore` logs each one as it reads it (`pkg/scraper/store.go`, "failed to parse definition file", with the path and the error), and the admin panel lists them under "Definition errors" when one is configured, so a broken YAML file doesn't just silently vanish. The log is the only surface on a headless install, which is why the reporting lives in the store rather than in a handler. The Torznab API does not report them: Jackett's indexer array has nowhere to put them.
- **One YAML escape is repaired before decoding** (`pkg/scraper/yamlcompat.go`, `unmarshalYAML`, used for definitions *and* config overrides so a regex in a double-quoted scalar is not refused in one file and accepted in the other): YAML 1.2 lists `\/` among the escapes a double-quoted scalar may use, and `gopkg.in/yaml.v3` — libyaml-derived, so YAML 1.1 — is the only parser in play that rejects it. It is the *only* YAML 1.2 escape it rejects, which is what keeps the repair this narrow. Every definition in Jackett's repository is expected to parse here, and one writing that escape is unusable for no other reason without the repair. `unmarshalYAML` runs `repairSlashEscapes` **only after a plain decode has already failed**, and keeps its result only if that then succeeds, so nothing that parses today can be changed by it; a failure is reported as the original error, which describes the file the operator wrote. The scanner has to know when it is inside a double-quoted scalar, and `opensScalar` is the subtle part: `:`, `-` and `?` are YAML indicators only when a blank follows them, so the closing quote of a plain scalar like `selector: td a[href*="/torrent-category-"]` must not be read as opening one — getting that wrong leaves every later line of the file inside a scalar that was never opened.
