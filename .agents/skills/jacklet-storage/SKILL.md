# Storage

`pkg/database` keeps scraped torrents in SQLite as a cache any search can refill. One server process uses it concurrently through a single connection, which shapes most of what follows. Read the entry for a behavior before changing it.

## Using SQLite

- **Every store operation takes a context**: all database calls use the `…Context` variants, threaded from the request (`r.Context()`), the scrape, or the shutdown signal — `noctx` enforces this outside tests. It matters more here than usual: the pool is capped at one connection, so an uncancelable query started by a client that has since disconnected blocks every other request until it finishes on its own.
- **SQLite is configured for a concurrent server**: `database.Open` appends `_pragma` settings to the DSN (WAL journaling, a 5s busy timeout) and caps the pool with `SetMaxOpenConns(1)`. SQLite serializes writers, so without this concurrent scrapes fail with `SQLITE_BUSY` and silently drop rows. Every read and write of the table goes through `database.Store`, so no other package imports `database/sql` or writes SQL. It also creates `idx_torrents_tracker_published` on `(tracker, published DESC, id DESC)`, the access pattern every listing uses — the `UNIQUE(tracker, identity)` index can't serve the sort. `torrent_searches` gets `idx_torrent_searches_torrent_id` because a torrent's delete cascades to its searches by `torrent_id`, which its primary key does not lead with; without it every pruned torrent scans the whole table while the single connection is held. A torrent's `identity` is a generated column (info hash, else details URL, else title), so same-titled releases stay distinct rows.
- **Name matching folds case in Go, not in SQL**: SQLite's `LIKE` and `lower()` fold case for ASCII only, so a Cyrillic query would never match a stored Cyrillic title. `pkg/database`'s `search.go` registers a `unicode_lower` SQL function with the driver and applies it inside `Store.Search` through the unexported `nameMatchClause`, so `pkg/torznab` and `pkg/admin` get folded matching by going through the store — don't write a bare `name LIKE ?` anywhere. Registration happens in `Open` before `sql.Open`, since the driver only applies a function to connections opened afterwards.

## The schema

- **The schema is authoritative and never migrated**: `createSchema` (run by `Open`) creates the table and stops there — no `ALTER TABLE` path, no per-version migration code. The torrents table is a cache that any search refills, so a schema change is answered by deleting the database file, not by carrying every past shape forward. Every column is `NOT NULL` with a default, which makes a NULL unrepresentable and is why reads need no `COALESCE` and no `sql.NullString`; keep it that way when adding a column. The file is stamped with `schemaVersion` in SQLite's `user_version`, because `verifySchema` can only see that columns resolve: a change it cannot see (a different `identity` expression, a column that means something new) would let an older cache open and write rows that disagree with the ones already there. A database stamped with another version is refused with the same delete-and-restart message, one no build has stamped is vetted by its columns and adopted, and `schemaVersion` is bumped with any such change.

## Rows

- **A row's categories are one column** (`categories`, `categoryList`): the ids joined by commas, in the order the scrape gave them. A category filter matches a row holding any one of the requested ids, through `categoryMatch`, which wraps the column and the bound id in commas so an id is only ever matched whole: 204 never matches a row in 2040, nor 2040 one in 20400.
- **Re-scraping refreshes rows, it doesn't skip them**: `Store.Upsert`/`Store.UpsertAll` upsert (`ON CONFLICT(tracker, identity) DO UPDATE`), so swarm counts, size and categories are updated each time a torrent is seen again. A plain `INSERT` whose conflict was swallowed would freeze every row at its first-seen values and defeat re-scraping.
- **Stored fallback preserves the whole search**: scraper-managed rows are associated with `SearchParams.ResultKey`, which covers every result-shaping Torznab parameter but omits local paging. `scraper.Query.QueryKey` uses that provenance when a scrape fails, so an identifier, season, year, genre or other structured search cannot fall back to unrelated rows that merely share title words. Rows written through the public `Store.Upsert`/`Store.UpsertAll` methods remain generic library-managed cache entries and are not forced into scraper query provenance; a search by external ids alone, which has no terms to match their names on, takes only those stored with one of its ids and contradicting none (`scraper.Query.IDs`, `scraper.ExternalIDs`), each compared as a number, while a search with terms matches them by name; a search's episode narrows only these rows (`scraper.Query.UnsearchedTerms`), since the tracker matched it for the rows it returned, which may write it some other way.
- **Retention**: `database.Prune` deletes torrents whose `published` date is older than the window `JACKLET_RETENTION_DAYS` sets (30 days by default; `0` disables pruning and skips the sweep goroutine entirely); `main.go` runs it every `pruneInterval` (1h). The cutoff uses the release date scraped from the tracker when available. The `published` column is stored as UTC RFC 3339 so this comparison can be lexicographic, and is left empty rather than zero-valued when no date parsed; those rows age from the internal `last_seen` timestamp instead, so a tracker that omits dates cannot grow the cache forever.
