# Torznab API

Clients reach Jacklet by pasting a Jackett URL, so the API answers at Jackett's addresses and in Jackett's shapes, down to inconsistent key casing, and each divergence from Jackett described here is deliberate. Read the entry for a behavior before changing it.

## Routes

- **The URL space is Jackett's, not Jacklet's own** (`Torznab.Routes`, `pkg/torznab/routes.go`, the single place every route is declared — `main.go` reaches it through `jacklet.Stack.Routes`, and the tests call it too, so they exercise production routing; `Torznab.Handler` wraps it as an `http.Handler` for a program routing some other way, and must be mounted at `/api/v2.0/` without stripping the prefix, since the paths are fixed): Torznab specifies query parameters and a response format but no URL layout, so there is no spec-blessed path to prefer, and Jackett's layout is what every client is configured with, since an operator sets one up by pasting a Jackett URL. Choosing anything else buys nothing and costs compatibility. One endpoint has no Jackett counterpart and is marked as Jacklet's own in `Routes`; everything else answers at the address Jackett serves it from. **A new endpoint goes where Jackett puts it, or is labeled as Jacklet's own where it is declared.**

  Jackett's CouchPotato-era surface is deliberately not served, and its absence is not an oversight to be corrected: no `/results/potato`, and the apikey is read from `apikey` alone, not from Jackett's `passkey` alias, which exists only for that same client. Every maintained Torznab client (Sonarr, Radarr, Lidarr, Readarr, Prowlarr) sends `apikey`. Jackett's indexer management and server-configuration routes are absent for a different reason: they act on a per-indexer configuration lifecycle Jacklet does not have, since a definition is a file in `definitions/` rather than something switched on, which is also why every indexer reports `configured` as true.
- **Per-indexer endpoints, plus one aggregate**: `GET /api/v2.0/indexers/{id}/results/torznab` serves exactly one tracker definition (matched by its YAML `id` field via `DefinitionStore.Find`). Jackett routes the torznab action as `[action]/{ignored?}`, so the trailing segment is optional and its value means nothing — clients send `api`, and `Routes` registers both forms. `GET /api/v2.0/indexers` lists every definition for discovery when configuring Sonarr/Radarr/Prowlarr. Per-indexer endpoints remain the recommended setup, since they let the client retry and disable each tracker on its own — the aggregate exists for clients that would rather add one URL.
- **`GET /{$}` redirects to `/docs`**: the exact root path only (Go 1.22 `{$}` pattern), so `public/`'s lack of an `index.html` doesn't turn `GET /` into a raw directory listing; every other static path (e.g. `/openapi.yaml`) still falls through to the `http.FileServer` catch-all.

## The aggregate indexer and filters

- **The aggregate indexer (`torznab.AggregateID`, `"all"`)**: `/api/v2.0/indexers/all/results/torznab` and `/api/v2.0/indexers/all/results` answer from every configured definition able to answer the search, as `handles` decides. Both kinds of request are resolved by `Torznab.authorizedIndexer` into an `indexer` (see `pkg/torznab/aggregate.go`) holding one definition or all of them, and `handleCaps`/`handleSearch`/`Results` work in terms of that, so neither has to ask which kind it is serving — a new search-shaped endpoint should take an `*indexer` too rather than a `*scraper.Tracker`. An `indexer` standing for a set rather than for one definition sets `IsMeta`, which is what `t=indexers` answers for. Covering no definitions is **not** by itself an error. A meta indexer built when *nothing loaded at all* sets `IsUnconfigured` and answers 503, because that is a broken install; the aggregate and a filter expression both do, since the install is equally broken whichever one the client addressed, and a client that reaches this API by filter rather than by id would otherwise be the only kind never told. What makes the two cases separable is that `IsUnconfigured` is recorded at construction from the *loaded* set, not derived afterwards from `Defs` — deriving it would turn every filter that simply matched nothing back into a 503. **That 503 is a deliberate divergence** — Jackett assigns its aggregate `Indexers = _indexers.Values`, an empty collection rather than null, so its `IsConfigured` is true and it answers the same request 200 with empty arrays. An operator whose `definitions/` directory is empty would otherwise see nothing but successful, permanently empty searches; the cost is that a client reaching this API before definitions are in place sees a provider error rather than an empty result. A filter that matched none of the configured definitions, or a `Tracker[]` naming none of the ones addressed, is an ordinary empty answer — and `search` returns it without reaching the store, since `scraper.Query` reads an empty `Trackers` list as *every* tracker rather than none and would otherwise hand back the entire store. Four rules the implementation depends on, each with a test in `pkg/torznab/aggregate_test.go`:
  - **One store query, not one per tracker**: `scraper.Query.Trackers` is a list and `Torznab.search` passes `indexer.ids()`, so the sort order, the page and the total are global. Merging per-tracker pages in Go afterwards cannot reproduce a correct `offset`/`total`, so don't.
  - **A failing tracker must not fail the search**: `Torznab.scrape` fans out concurrently (bounded by `maxConcurrentScrapes`) and returns an error only when *every* definition failed; partial failures are logged. A single indexer's endpoint keeps the stricter behavior, where its own failure is the request's failure.
  - **`t=indexers` is the aggregate's own operation** (`handleIndexerList`, `pkg/torznab/indexerlist.go`): it lists the definitions behind the aggregate, each carrying its *own* caps rather than the merged set, since the point of the list is what each indexer can do alone. Jackett serves this for a meta indexer only and answers error 203 for any other, so a single definition gets that error document rather than a list of one. Note `indexerEntry`'s fields are in document order, not alphabetical — `encoding/xml` emits elements in field order, so sorting them would reshape the response.
  - **Download links belong to the owning indexer**: `rowIndexerID` uses the row's stored `tracker`, so a link reads `/api/v2.0/indexers/<owner>/download/<row>`. There is deliberately no `.../indexers/all/download/...` — the aggregate is a search surface, not a download one. The JSON results carry the owner in `TrackerId` for the same reason.
  - **A panicking tracker is a failed tracker**: `Torznab.scrape` wraps each fan-out goroutine in `scrapeGuarded`, so a panic becomes that tracker's error and the request answers like any other partial failure — a 502 naming the cause when no tracker answered and nothing is stored to fall back on. Those goroutines are not the request's, so nothing above them recovers; a single indexer's endpoint needs no guard, being the request goroutine `net/http` recovers itself.
  `AggregateID` shadows a definition that uses `all` as its own id; `warnIfNoDefinitions` says so at startup.
- **Indexer filters stand in for an indexer id** (`pkg/torznab/indexerfilter.go`): `status:healthy`, `!type:private+lang:en`. Jackett resolves the same expressions at the same position in the path, and a client offering its user "all working indexers" rather than a list of them sends one, so the expression has to resolve here for that client to search at all. A colon is what marks an id as an expression — no definition id contains one. Two rules the implementation depends on. **Health is a deliberate divergence**: Jackett's `IsHealthy` is `errorCount == 0 && expireAt > now`, a validity window opened by a search that succeeded, so an indexer Jackett has not searched yet is *unknown* and `status:healthy` answers a freshly started instance with nothing — which would leave a client that offers only "all working indexers" unable to search until something else had searched first. Health here is the absence of a recorded failure instead, so a tracker nothing has scraped yet is healthy. Don't "fix" this to match Jackett without solving the cold-start case. (Jackett's `test:` filter *is* last-error based, `LastError == null`; Jacklet has no separate test action, so both names read the one state it keeps.) Second, an expression naming a filter Jacklet does not serve is a 404 rather than an empty match, since a client cannot tell "no indexer is healthy" from "I asked for something you ignored". Jackett has no answer to copy here: `GetWebIndexer` throws `Unknown indexer` for a name that parses as no filter, and nothing on the request path catches it, so the 404 with a JSON body is Jacklet's own. `tag:` is the one exception it answers empty for, because a definition is a file in a directory with nothing to hang a user's label on.

## Answers in Jackett's shapes

- **A search goes only to the trackers that can answer it** (`handles`, `indexer.handling`), as Jackett's `BaseIndexer.CanHandleQuery` decides, read from the modes each definition's caps advertise so that every advertised mode stays accepted: an IMDb id needs a movie search taking `imdbid`, or a TV search on a definition setting `allowtvsearchimdb`; any other search needs its mode, or a TV search taking the TVRage or TVDB id it names; a plain search is always available. A tracker that cannot answer a search would otherwise be scraped with nothing to search for and answer with its latest releases. When none of the trackers an indexer covers can answer, the XML feed refuses the search with a 400 carrying Jackett's error 201, as Jackett refuses it for the indexer addressed, rather than an empty feed a client would read as no releases; the JSON endpoint, Jackett's interactive search, which skips that refusal, answers with nothing. `search` reports the case on `searchResult.IsUnsupported` and leaves the answer to each endpoint (`TestHandles`, `TestTorznabHandlerRefusesASearchTheIndexerCannotAnswer`, `TestTorznabHandlerAggregateSearchesOnlyTheTrackersThatCanAnswer`).
- **One indexer directory, in Jackett's shape**: `GET /api/v2.0/indexers` (`Torznab.JackettIndexers`) answers in Jackett's own JSON — a bare array, its lowercased and underscored keys, and capitalized `ID`/`Name` inside each capability — so a script written against Jackett enumerates Jacklet's indexers unmodified. The inconsistent casing is Jackett's; do not tidy it, since a tidier spelling is one a Jackett client would not find, and `pkg/torznab/jackettindexers_test.go` asserts the wire bytes rather than round-tripping through the struct for exactly that reason. Fields Jacklet has no equivalent for (`last_error`, `potatoenabled`, `tags`) are sent as empty values, never omitted or null: Jackett always sends a value, and a nil Go slice marshals to `null`. `configured` is always true, because a definition is in `definitions/` or it is not — there is no step that turns one on — and Jackett's `?configured=true` filter is accepted and ignored for the same reason. The aggregate indexer is deliberately absent, or a client walking the list to add every indexer would add all of them twice. This is the only indexer listing: search modes and categories are in an indexer's caps document and parse errors are logged as definitions are read and shown in the admin panel when one is configured, so a second listing shape would be one more thing to keep in sync for data already served.
- **JSON results endpoint alongside the XML one**: `GET /api/v2.0/indexers/{id}/results` runs the same scrape-then-search pipeline as `GET /api/v2.0/indexers/{id}/results/torznab/api?t=search` (same params: `q`, `cat`, `season`, `ep`, `imdbid`, `tvdbid`, `limit`, `offset`) but returns JSON — Jackett's own address and Jackett's own idea, a convenience it layers on top of the Torznab spec (which is XML-only) rather than something the spec itself defines. `handleSearch` (XML) and `Results` (JSON) share `searchParamsFromQuery` and `search`/`toTorznabItem` — a schema/behavior change to the search pipeline (new param, different scrape error handling, etc.) belongs in the shared code, not duplicated into just one of the two handlers. `search`'s `isInteractive` marks the JSON endpoint as Jackett's interactive search and carries the ways Jackett's differs from its feed: it keeps a row filed under no category, and it reads the request as Jackett's `ApiSearch.ToTorznabQuery` does, in `interactiveSearch`. That is a plain search, giving the definition a `.Query.Type` of `search` whatever `t` a client sends (`TestTorznabHandlerResultsJSONAlwaysRunsAPlainSearch`); an episode at the end of the query, `S01E02`, `S01`, `E02` or `S01 E02` after a word boundary as .NET draws one, taken off into the season and episode; and a query that is then an IMDb id, read as Jackett's `SanitizedSearchTerm` and `GetFullImdbId` read it, made an IMDb lookup keeping only the categories, season and episode, with no mode, sent only to the trackers whose movie search takes an IMDb id, as `handles` decides, and answered from the store with no row a search did not produce unless it holds that id (`TestTorznabHandlerResultsJSONSendsAnIMDbLookupOnlyToTrackersSearchingByOne`, `TestTorznabHandlerResultsJSONReadsTheQueryAsJackettDoes`).
  - **The response is Jackett's `ManualSearchResult`, key for key** (`searchResults`, `searchIndexer`, `jackettResult` in `pkg/torznab/results.go`). Torznab is XML-only and defines no JSON variant, so there is no spec to follow here and nothing to gain from a shape of Jacklet's own: a client reaching this address is one written against Jackett and reads those keys literally. That is why they are PascalCase, why `Peers` carries the leecher count (Jackett subtracts the seeders before serializing it), why `Category` is a list, and why `Details` is emitted twice, also under the older `Comments` name — the one key here Jackett itself does not send.
  - **Nullable numbers read zero as absent.** Jackett's `ReleaseInfo` declares most of its counts `long?`/`double?` and sends null for a field a definition did not scrape. The store holds plain numbers, so zero is the only signal of absence available, and `optional` in `pkg/torznab/results.go` turns it into null — the same reading `attributes` already takes for the Torznab feed, where such a field is left out rather than emitted as 0. `Seeders`, `Peers`, `DownloadVolumeFactor` and `UploadVolumeFactor` are exempt and always numbers: zero is an answer for each (an empty swarm, a freeleech), and the scraper defaults both factors to Cardigann's 1, so neither is ever unset. Don't extend `optional` to them — reporting null there would lose the common case to describe the rare one. Making the rest genuinely distinguishable would mean nullable columns in the store, which is a schema change rather than a rendering one.
  - **Three places it must not follow the XML feed.** It accepts the parameter names Jackett binds there (`Query`, `Category`/`Category[]`, `rageid`, `Tracker[]`, matched case-insensitively and with the brackets stripped — see `searchQuery`), since a client written against Jackett sends those and a search that ignored them would answer with unrelated latest releases rather than with nothing. Jackett's `ApiSearch` is the whole list of what it binds at that address: it reads neither `q` nor `cat` there, so those are Jacklet's addition rather than Jackett's. It answers unpaged (`jsonLimits`), since `ApiSearch` has no limit or offset at all. And an unreachable tracker is a 200 with the failure recorded against that indexer in `Indexers[]`, not a 502 — the shape has somewhere to put it, and a request covering several indexers must not lose the ones that answered. The XML feed keeps the 502 because an RSS document has nowhere to report a failed indexer. That 502 names only the indexer (`Indexer <id> is unreachable`), and a failed indexer in the JSON results says only `indexerSearchFailed`; the cause is logged in both, since it names the tracker's address and may carry a passkey in a shape redaction does not recognize.
  - **The spec's two search endpoints document different parameter lists.** `jsonOnlyParams` in `pkg/torznab/openapi_test.go` names the ones only the JSON endpoint takes, and each is there because Jackett itself binds it only at that address. The parameter tests walk both paths for the same reason.
- **Three failure formats, one per endpoint kind** (`pkg/torznab/errors.go`): the Torznab XML endpoint answers with `<error code description/>`, the JSON endpoints with `{"error": …}`, and a download with a bare status, since a `.torrent` is no document the client was going to parse. The shared pipeline (`authorizedIndexer`, `findAuthorizedTracker`, `search`) does not choose: each entry point passes its own `errorWriter`, and every one of them takes the Torznab code even though only the XML writer renders it, because the code describes the failure and not the rendering. **A new failure path takes the `errorWriter` it was handed rather than reaching for `http.Error`**, or the endpoint silently answers in a format its client does not parse. The codes are Jackett's own, from its `RequiresApiKey`/`RequiresConfiguredIndexer` filters and the torznab action: 100 rejected key, 201 unknown indexer, 203 function not available, 900 catch-all — plus 202 for an unknown `t`, which is Newznab's, since Jackett treats anything it does not recognize as a search. Jacklet keeps its own status codes (502 for an unreachable tracker, where Jackett sends 400), because the status describes the failure more precisely and the client branches on the code.

## Searching

- **`t=` query parameter values, not the caps XML element names**: Sonarr sends `t=tvsearch`, Radarr sends `t=movie` — the *unhyphenated* Newznab/Torznab spec values — not `tv-search`/`movie-search`, which only exist as XML element names inside the caps response (`<tv-search>`, `<movie-search>`). `ServeHTTP`'s switch accepts both forms defensively; don't narrow it to just the hyphenated ones, since that breaks TV/movie search against real Sonarr/Radarr while still looking fine against anything that queries with `t=search`.
- **Caps come from the definition**: `searchingCaps` renders `caps.modes` (via `scraper.SearchModes`, which falls back to a generic keyword-search set when a definition declares none) into the Torznab `<searching>` element, so a music or ebook tracker is advertised as able to serve those searches. Don't advertise a hardcoded set of modes instead. A definition setting `caps.allowrawsearch` marks every mode element `searchEngine="raw"`, available or not, as Jackett marks them (`indexer.allowsRawSearch`), which tells Sonarr and Radarr they may send a release title unsanitized; a meta indexer is marked when any of its trackers is, as Jackett's aggregate is. It changes nothing about how the search itself is made.
- **A tracker's own custom categories are listed only where one tracker is** (`indexer.categories`, `scraper.CustomCategories`): a single indexer's caps, its `t=indexers` entry and its directory entry list them after the standard categories, as Jackett does, while a meta indexer (the aggregate or a filter) lists the union of standard categories alone, because a custom number is one tracker's own and names a different category, or none, on the next. A result's `CategoryDesc` names standard categories only (`categoryNames`), as Jackett's does, even though its `Category` list carries the custom id.
- **Every advertised mode must be servable**: `handleCaps` derives `<searching>` from `caps.modes`, and `ServeHTTP`'s `t=` switch must accept a value for each mode it can advertise (`music`/`audio`/`book` as well as `search`/`tvsearch`/`movie`, hyphenated and unhyphenated). Advertising a mode the switch rejects makes a client take Jacklet up on an offer it then answers with 400. `TestTorznabHandlerAcceptsEveryAdvertisedMode` pins the two together.
- **Pagination**: `searchParamsFromQuery` reads `limit` (default 50, capped at `maxLimit`=100) and `offset` from the query string; `Store.Search` applies them via SQL `LIMIT`/`OFFSET` and reports the full match count across all pages (a separate `COUNT(*)` query) as `total`, not just the current page's row count. Keep `defaultLimit`/`maxLimit` in sync with the values advertised in `torznab.Limits` in `handleCaps`.
- **A failed scrape falls back to the store, it doesn't fail the request**: `handleSearch` and `Results` both run `search` before deciding what a scrape error means, and return 502 only when there is also nothing stored for that indexer. The store exists so a tracker outage degrades to stale results rather than to none; `openapi.yaml` documents that contract.

## Where results and definitions come from

- **Results reach the handlers through an interface too** (`torznab.Catalog`: `Find` and `Search`): `torznab.New` takes a `Catalog`, not a `*database.Store`, so a program embedding `pkg/torznab` can serve the API over its own storage without carrying a SQLite driver, and `TestPackageImportsNoStorage` fails if the package ever imports `pkg/database` again. `*database.Store` satisfies it unchanged. The interface is small and its contract is not: `Search` has to answer `scraper.Query` exactly as documented there — newest release first, the total counted across every page, terms folded case-insensitively for non-ASCII text too, the category and tracker lists as filters (an empty tracker list meaning every tracker), and `QueryKey` limiting scraper-managed rows to those a matching search produced — because the stored fallback and the aggregate's global paging both stand on it. `catalogtest.Run` (`pkg/torznab/catalogtest`) is that contract as an exported test suite. `fakeCatalog` — a small in-memory implementation in `pkg/torznab/catalog_test.go` that also serves as a `scraper.Sink` — runs it directly, and `database.Store` runs it through `storetest.Run` (`pkg/admin/storetest`, the same cases plus `Stats`'s own), so a change to what `Search` promises is made in one place and every implementation is held to it; a case is added there when the contract grows. `pkg/admin` takes an `admin.Store` — a `Catalog` plus `Stats`, the per-tracker figures the dashboard shows — and imports no storage package either, guarded by its own `TestPackageImportsNoStorage`; the dashboard's total is the sum of the `Stats` figures, and a `Stats` error is what it reports as an unreachable store, still rendering the page. The panel's test button shows the newest rows produced under that test search's `ResultKey`, read back from the store and not taken from the scrape's return, because a download link is the store's row id and a scrape leaves it zero.
- **Definitions reach the handlers through an interface**: `torznab.New` takes a `scraper.TrackerSource` (`Find`, `Trackers`), not a directory path, so a program embedding `pkg/torznab` can serve definitions from a database, a remote service, or memory instead of YAML files on disk — `pkg/` is a library surface, and the directory layout shouldn't be baked into the handler. `main.go` injects a `DefinitionStore`. An implementation must be safe for concurrent use and must not hand back a `Tracker` aliasing state it later mutates.
