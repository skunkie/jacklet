# Repository Agent Instructions

## Project Goal

Jacklet is a lightweight Go alternative to Jackett: a single-binary Torznab/Newznab-compatible indexer proxy that scrapes torrent sites via YAML-defined rules instead of embedding a JVM or a large plugin runtime. Favor a small footprint and minimal dependencies over feature parity with Jackett's full plugin ecosystem.

Jacklet aims to reuse Jackett's own indexer definitions directly, with full compatibility with Jackett's YAML definition format (as used in [Jackett/Jackett's](https://github.com/Jackett/Jackett) `Definitions/` directory), so existing Jackett indexer definitions can be dropped into `definitions/` without modification.

## Commit Messages & History Hygiene

- **Conventional Commits**: Use `type(scope): concise imperative summary`.
- **Specific Scopes**: Use a specific package or subsystem as the scope when appropriate, for example `fix(scraper): ...`, `feat(torznab): ...`, or `refactor(database): ...`. Omit the scope for genuinely cross-cutting changes, as in `test: ...`.
- **Subject Formatting**: Keep the subject concise, lowercase after the colon, and without a trailing period.
- **Atomic Commits**: Treat one cohesive change and its supporting refactors and tests as one commit, even when it touches multiple packages. Split changes only when they are independently meaningful and leave the repository correct at each boundary.
- **Body Requirements**: For a non-trivial commit, add a body after a blank line and use `-` bullets. Write each bullet as a complete sentence ending with a period.
- **Content Focus**: Use body bullets to describe observable behavior, important implementation or safety details, and relevant test coverage. Do not narrate file-by-file edits.
- **Timestamp Symmetry**: When rebasing, amending, or squashing commits, ensure `GIT_COMMITTER_DATE` matches `GIT_AUTHOR_DATE`.
- **Atomic Buildability**: Ensure every commit compiles and verifies cleanly: run `go build ./...`, `go test ./...`, `golangci-lint run` (config in `.golangci.yml`), and `reuse lint`.

Example:

```text
fix(scraper): handle missing release date on listing page

- Fall back to the torrent detail page when the listing omits a release date.
- Skip entries whose date cannot be parsed instead of aborting the scrape.
- Add coverage for missing and malformed date fields.
```

## Naming Conventions

- Follow standard Go naming: `PascalCase` for exported identifiers, `camelCase` for unexported ones. Use `UPPER_SNAKE_CASE`-style only for environment variable names (`PORT`, `API_KEY`), never for Go identifiers.
- Choose clear, descriptive names based on domain behavior. Avoid ambiguous abbreviations, single-letter identifiers outside small conventional scopes (loop indices, receivers), and names that repeat obvious type information.
- Name booleans with predicates such as `is`, `has`, `can`, `should`, or `needs`, so a flag reads as a flag where it is branched on. Three surfaces keep a bare adjective or participle instead, each because the name's audience is something other than a Go call site:
  - **Fields an HTML template renders**, and the status values copied field-for-field into them. The admin panel's view structs (`pkg/admin/handlers.go`) are read as `{{ if .Authenticated }}` and `{{ if .Secret }}`, where the prefix is noise in the template and the field name is part of the template's contract rather than of any caller; `scraper.IndexerStatus`'s `Authenticated` and `Scraped` are copied straight into those views and carry the same names so the two sides stay legibly one thing.
  - **Toggles in an `Options` struct**, where a keyed literal already reads as an assertion: `admin.Options{SecureCookies: true}` says what it turns on, while `Options{ShouldUseSecureCookies: true}` says it twice.
  - **Fields whose name is their own wire tag**, PascalCased: `CategoryMapping.Default` (`yaml:"default"`), `SearchPath.FollowRedirect` (`yaml:"followredirect"`), `Field.Optional` (`yaml:"optional"`), `Caps.AllowRawSearch` (`yaml:"allowrawsearch"`). Every tagged field in `pkg/scraper/definitions.go` is named after its own key, so the struct can be read against a Cardigann definition line for line; prefixing the handful that happen to be booleans would make them the only fields that don't match. This is the wire-format rule below, not an exception to it — "idiomatic Go name" there means PascalCasing the key, not substituting a different word.
  - The exemption is about where a name is *read*, not about avoiding a rename. A bool with no template audience and no wire tag of its own takes the predicate.
- Prefer a typed value (`time.Duration`, not a raw `int` of milliseconds) over embedding units in a name. When a raw numeric can't avoid ambiguity — typically at a JSON/YAML/XML boundary — include the unit in the name (e.g. `sizeBytes`).
- Preserve field names defined by external wire formats — Cardigann's YAML definition schema (`categorymappings`, `legacylinks`, `re_replace`, ...) and the Torznab/Newznab XML attributes — via struct tags rather than renaming the wire format to fit Go idiom. Use idiomatic Go names for the Go-side fields themselves and let the tag carry the external name — which means PascalCasing the external key (`re_replace` becomes `ReReplace`), not renaming the concept, so a struct stays readable against the document it models.
- Reuse established Torznab/Cardigann terminology instead of inventing synonyms for the same concept (e.g. "tracker" vs "indexer" vs "provider" — pick one and stay consistent).
- **Alphabetical struct fields**: sort a struct's field declarations alphabetically by name, case-sensitive (plain byte order), including unexported fields. When a struct mixes exported and unexported fields, case-sensitive order clusters exported fields first (each block alphabetized internally), matching Go's own convention of leading with a type's public surface — don't fold case to force a single interleaved list. Sort a composite literal's named fields to match when practical. This is a plain ordering rule, not a semantic one — it doesn't override Go requirements like an embedded field needing to come first for promotion, and doesn't apply to enum-style `const` blocks whose order is meaningful (e.g. `iota` sequences). It also doesn't apply where declaration order *is* the wire format: `encoding/xml` emits elements in field order and offers no tag to reorder them, so `torznab.Channel` and `torznab.Item` are declared in the order RSS 2.0 requires them to be serialized. A struct taking this exemption says so in its doc comment.

## Code Comments & Documentation

- Default to no comments. Only add one when the *why* is genuinely non-obvious: a hidden constraint, a subtle invariant, or behavior that would otherwise surprise a reader.
- **A declaration's explanation goes above it, not inside it**: a comment that says what a function, type or test is *for* belongs on the line before `func` or `type`, as its doc comment; a comment inside the body belongs to the statement it sits above. The split is what lets a reader learn what something is for without reading it, and it is what `go doc` and an editor's hover show. Tests are declarations too — the reason a test exists goes above `func TestX`, while a note about one step stays beside that step, and a step comment must not be promoted just because it happens to be the body's first line. Where the reason is per-assertion rather than per-test, `require`'s message argument already carries it and no comment is needed.
- Do not narrate bug history in comments — no references to a specific error message, a prior regression, "this used to crash", or how an issue was found and fixed. That narrative belongs in the commit message, not the source; comments rot as the codebase evolves while commit history stays accurate.
- Rely on regression tests, not comments, to prevent a fixed bug from resurfacing. A test that reproduces the original failure is durable; a comment warning "don't do X, it broke before" is not enforced and will be forgotten or contradicted by the next edit.
- Make a comment's explanation self-contained rather than pointing to AGENTS.md or another external doc for the reason. Docs and code can be edited independently and drift out of sync, silently turning "(see AGENTS.md)" into a dead pointer; a reference to another function or type in the same file is fine, since it moves and changes together with the comment.
- This applies beyond source comments: other project documentation (`README.md`, `docs/*.md`) should also explain things in its own words rather than citing "AGENTS.md" or a specific rule by name, for the same reason.
- **No hardcoded counts or measured results in documentation**: don't write a figure that was true when you measured it — how many definitions parse, how many tests there are, a benchmark timing, a file or package count, a coverage percentage. It is a record of one run against one snapshot, it goes stale the moment either side changes, and nothing in the build checks it. State the standard the code is held to instead ("every definition in Jackett's repository is expected to parse"), and point at the endpoint, command or output that shows the reader the current figure. The same goes for narrating a past run — what a check caught, what once failed and was fixed — which belongs in the commit message for the same reason bug history does.
- Describe behavior in terms of what it does, not what it used to do or doesn't do relative to some other design (e.g. "there is no single endpoint aggregating results" implies a former or expected alternative). State the actual behavior directly instead of contrasting it against an absent or prior one.

## Build & Test

- **Backend Unit Tests**: Run Go package test suites:
  ```bash
  go test ./...
  ```
- **Static Analysis**: Run `golangci-lint run` (config in `.golangci.yml`, adapted from TorrPlay's), which covers `go vet` plus `gosec`, `gocritic`, `staticcheck`, and other linters.
- **Assertions are `testify/require`**: every test asserts through `github.com/stretchr/testify/require` — no hand-rolled `if got != want { t.Errorf(...) }`, and no mixing `require` with `assert` for the same kind of check. One assertion vocabulary across packages is what lets a reader move between `pkg/scraper` and `pkg/torznab` without re-learning how a failure is reported, and `require`'s messages already name got and want, so a third argument is for the *reason* a check matters ("the stored password was rendered into the page"), not a restatement of the values.
  - **`assert` is the deliberate exception, in two places.** Where a loop is meant to report every failure in one run — `pkg/torznab/openapi_test.go` walks the whole spec, and stopping at the first drift would hide the rest of the work — and where an assertion runs off the test's own goroutine (an `httptest` handler, a `wg.Go` worker), since `require` calls `t.FailNow`, which `testing` only permits on the goroutine running the test. Reach for `assert` for one of those two reasons or not at all.
- **Test Coverage & Regression Prevention**:
  - Accompany every bug fix, refactor, and new feature with dedicated unit tests covering edge cases and error paths.
  - Run package test coverage profiles to verify complete path coverage:
    ```bash
    go test -cover ./...
    ```
- **Documentation name check**: when a change renames, removes or unexports anything, confirm the docs don't still name it. This scans every backticked identifier in `AGENTS.md`, `README.md` and `docs/*.md` and reports the ones no longer present in `pkg/` or `cmd/`:
  ```bash
  python3 - <<'EOF'
  import pathlib, re
  files = [pathlib.Path("AGENTS.md"), pathlib.Path("README.md"), *sorted(pathlib.Path("docs").glob("*.md"))]
  docs = "".join(f.read_text() for f in files)
  token = re.compile(r"\"(?:\\.|[^\"\\\n])*\"|`[^`]*`|'(?:\\.|[^'\\\n])*'|//[^\n]*|/\*.*?\*/", re.S)
  def strip(path):
      return token.sub(lambda m: "" if m.group()[0] == "/" else m.group(), path.read_text())
  code = "".join(strip(p) for d in ("pkg", "cmd") for p in pathlib.Path(d).rglob("*.go"))
  names = {n for n in re.findall(r"`([A-Z]\w*(?:\.\w+)?)`", docs) if not n.isupper()}
  stale = sorted(n for n in names if n.split(".")[-1] not in code)
  print("\n".join(stale) or "docs name no missing identifiers")
  EOF
  ```
  Comments are stripped first, so a name kept alive only by a stale comment still counts as gone. They are matched in the same alternation as string and rune literals, and each file is stripped on its own, because a path glob such as `templates/*.html` opens a block comment as far as a bare comment regex is concerned. `pkg/admin` has one in a `//go:embed` line and another in a `ParseFS` argument, so a regex that reaches for the next `*/` on its own runs forward from there and deletes everything up to the next block comment in the tree — every identifier in what it ate then reads as missing. Scanning the literals too means whichever opens first wins, so a `/*` inside a string is read as part of that string rather than as a comment. The literals themselves are kept, so a name that appears only in a struct tag still counts as present. It is a prompt to look, not a gate: prose in backticks (`PascalCase`) shows up as a false positive, and it cannot tell a renamed symbol from a deleted one. Run it after any such change.
- **Invented sample data, never real works**: sample titles in code, tests, fixtures, and documentation must be made up — "Example Release", "Sample Show S01E02", "Test Artist" — not the names of real films, series, albums, books, or the people who made them. Jacklet indexes torrent trackers, so a fixture naming a real, in-copyright work reads as a reference to a specific pirated release rather than as neutral test data, which is not something the project should have committed to it. Invented names are also better test data: they cannot collide with a real result during manual testing, they make an assertion's intent obvious, and they never date.
  - This covers a test's own strings as well as any HTML or JSON fixture captured from a live site: scrub a recorded page before committing it rather than saving the tracker's real listing verbatim.
  - Names that identify software and protocols are not sample data and are expected — Jackett, Cardigann, Sonarr, Radarr, Prowlarr, FlareSolverr, Torznab.
  - Definitions are exempt, and are git-ignored besides: they are upstream data mirrored from Jackett, and a tracker's own `categorymappings` descriptions sometimes name real franchises. Editing one to satisfy this rule would break the compatibility the project exists for. If a definition is ever needed for a test, write a fictional one inline rather than committing a real site's.
  - Non-ASCII coverage still matters (see the Cyrillic case-folding tests), so invent non-ASCII sample titles rather than dropping the coverage: "Тестовый Релиз" makes the same point as a real Russian film title.
- **Test terminology**: use precise testing terms across tests, fixtures, and helpers. These names are load-bearing rather than house style: they carry their established test-double meanings, so a reader who sees one knows what to expect without reading the body. Calling an `httptest.Server` a "mock" sends them looking for call-count assertions that are not there, and calling a canned HTML string "fake" suggests a working implementation stands behind it.
  - **`sample`**: a fed-in value, where it needs separating from the result it produces or from a real value alongside it (`sampleNonUnicodeName` next to `expectedDecodedName`). Most synthetic data is a bare literal that needs no prefix; what those literals may contain is the rule above, not this one.
  - **`test...` / `fixture`**: canned payloads, HTML snippets, and static definition files (`testHTML`, `testDef`, `test-tracker`).
  - **`testServer`**: an `httptest.Server` serving canned responses (or descriptive role names such as `site` or `tracker`).
  - **`stub`**: an implementation of an interface that returns fixed, usually empty answers so a test can reach the code under test (`stubRow`). It records nothing and asserts nothing.
  - **`fake`**: reserved exclusively for an in-memory, working implementation of an interface (such as an in-memory store or clock).
  - **`mock`**: reserved exclusively for objects pre-programmed with call expectations that verify method invocations.

  The `test` prefix is always available and is *required* only where a bare name would mislead: where it collides with another value in the same test — `testDef` beside the parsed `def` — or where the plain noun reads as the thing under test rather than as the canned input to it. A descriptive role name (`site`, `tracker`, `page`) is equally good and often says more. So `testServer`, `tracker` and, in a short test that holds only one, `server` are all fine; what the rule rules out is a name that leaves a reader guessing which side of the test they are looking at. This is a review convention, not a lint: it settles the confusing cases and deliberately leaves the clear ones to taste.

  `stub`, `fake` and `mock` are the opposite: they are claims about behaviour, so use them only when the definition above holds, and never as a generic label for canned data.

## Architecture

- `pkg/scraper`: fetches and parses indexer site pages (definitions in `definitions/*.yml`) into torrent listings, applies Cardigann-style field filters, and maps site categories to standard Torznab categories.
- `pkg/torznab`: exposes scraped results over the Torznab/Newznab-compatible API.
- `pkg/database`: persists scraped torrents in SQLite.
- **Every store operation takes a context**: all database calls use the `…Context` variants, threaded from the request (`r.Context()`), the scrape, or the shutdown signal — `noctx` enforces this outside tests. It matters more here than usual: the pool is capped at one connection, so an uncancellable query started by a client that has since disconnected blocks every other request until it finishes on its own.
- **SQLite is configured for a concurrent server**: `database.Open` appends `_pragma` settings to the DSN (WAL journaling, a 5s busy timeout) and caps the pool with `SetMaxOpenConns(1)`. SQLite serializes writers, so without this concurrent scrapes fail with `SQLITE_BUSY` and silently drop rows. Every read and write of the table goes through `database.Store`, so no other package imports `database/sql` or writes SQL. It also creates `idx_torrents_tracker_published` on `(tracker, published DESC, id DESC)`, the access pattern every listing uses — the `UNIQUE(tracker, identity)` index can't serve the sort. A torrent's `identity` is a generated column (info hash, else details URL, else title), so same-titled releases stay distinct rows.
- **Re-scraping refreshes rows, it doesn't skip them**: `Store.Upsert`/`Store.UpsertAll` upsert (`ON CONFLICT(tracker, identity) DO UPDATE`), so swarm counts, size and category are updated each time a torrent is seen again. A plain `INSERT` whose conflict was swallowed would freeze every row at its first-seen values and defeat re-scraping.
- **Stored fallback preserves the whole search**: scraper-managed rows are associated with `SearchParams.ResultKey`, which covers every result-shaping Torznab parameter but omits local paging. `database.Search.QueryKey` uses that provenance when a scrape fails, so an identifier, season, year, genre or other structured search cannot fall back to unrelated rows that merely share title words. Rows written through the public `Store.Upsert`/`Store.UpsertAll` methods remain generic library-managed cache entries and are not forced into scraper query provenance.
- **Retention**: `database.Prune` deletes torrents whose `published` date is older than the window `JACKLET_RETENTION_DAYS` sets (30 days by default; `0` disables pruning and skips the sweep goroutine entirely); `main.go` runs it every `pruneInterval` (1h). The cutoff uses the release date scraped from the tracker when available. The `published` column is stored as UTC RFC 3339 so this comparison can be lexicographic, and is left empty rather than zero-valued when no date parsed; those rows age from the internal `last_seen` timestamp instead, so a tracker that omits dates cannot grow the cache forever.
- **`pkg/` is a public library surface**: `cmd/jacklet` is one consumer of `pkg/scraper`, `pkg/torznab`, and `pkg/database`, not the only intended one — another Go program should be able to import them directly to embed indexer scraping without running Jacklet's HTTP server. Give every exported identifier a doc comment (`golangci-lint`'s `revive` `exported` check enforces this) and each package a package-level doc comment. A knob that is deployment-specific rather than part of a tracker definition goes in that package's `Options` struct, reached through a `New…WithOptions` constructor while the plain `New…` keeps the defaults (`scraper.Options`, `torznab.Options`).
- **A definition's `encoding:` applies to the request, not just the response**: `encodeForm` transcodes the submitted form into the tracker's character set before percent-encoding it, and sets the charset on the POST `Content-Type`. A windows-1251 tracker sent UTF-8 search terms does not fail — it reads the query as mojibake and silently returns its default listing, so this is pinned by asserting the bytes actually sent (`TestScraper_EncodesFormInTrackerCharset`), not by whether a scrape succeeds.
- **Name matching folds case in Go, not in SQL**: SQLite's `LIKE` and `lower()` fold case for ASCII only, so a Cyrillic query would never match a stored Cyrillic title. `pkg/database`'s `search.go` registers a `unicode_lower` SQL function with the driver and exposes `NameMatchClause`, which `pkg/torznab` and `pkg/admin` both use — don't write a bare `name LIKE ?` anywhere. Registration happens in `InitDB` before `sql.Open`, since the driver only applies a function to connections opened afterwards.
- **A size with no unit is a byte count**: many definitions select a site's raw size field rather than a human-readable one, so `parseSize` treats a bare number as bytes. An unrecognized *unit* is still an error, so a mis-parsed size is never mistaken for a real one.
- **The schema is authoritative and never migrated**: `InitDB` creates the table and stops there — no `ALTER TABLE` path, no per-version migration code. The torrents table is a cache that any search refills, so a schema change is answered by deleting the database file, not by carrying every past shape forward. Every column is `NOT NULL` with a default, which makes a NULL unrepresentable and is why reads need no `COALESCE` and no `sql.NullString`; keep it that way when adding a column.
- **`torrentFrom` maps every Cardigann field Jackett does, and parses them the way Jackett does.** The numeric fields go through `coerceLong`/`coerceDouble`/`parseSize`, which mirror `ParseUtil`: they keep the digits and treat both `,` and `.` as digit grouping. This leniency is the whole point — a tracker rendering "1,234" seeders or a "0,5" volume factor is ordinary, and a strict `strconv` parse turns the first into zero (a release that looks dead and gets discarded) and the second into the default 1 (a half-leech release advertised as fully counted). `coercePeerCount` additionally zeroes a count at or above 5,000,000, which is Jackett's guard for placeholder columns that parse into an enormous number. The `date` field is resolved with `parseUnknownTimeValue`, the same heuristics as the `fuzzytime` filter, because Jackett applies `FromUnknown` here and a definition is therefore not required to declare a date filter at all.
- **External ids are stored as digits, and the poster attribute is called `coverurl`.** `extractDigits` mirrors `ParseUtil.GetLongFromString`, so a field holding `tt1234567` or `tmdb/955` stores just the number, which is what Jackett puts in the attribute. `genre` is normalized by `parseGenres` — split on the same delimiters `validate` uses, `_` becomes a space, repeats dropped, joined with ", ". Note two names that do not match their Cardigann field: the `poster` field is served as the **`coverurl`** attribute, and `imdb`/`imdbid` are one field in Jackett, so `torrentFrom` reads both spellings and stores the digits. The feed then emits the id **twice** — `imdb` as the bare number zero-padded to seven (`imdbNumber`) and `imdbid` as the canonical `tt` form (`IMDBID`), which is also what the JSON endpoint reports — because clients look for one name or the other. Neither is emitted when nothing was scraped, deliberately unlike Jackett, which emits `tt0000000` for a row whose imdb field was empty and invites a client to match on it. When adding a media field, it has to land in all four places — `database.Torrent`, the schema, `torrentColumns`/`scanTorrent`/`upsertSQL`/`upsertArgs`, and `torznab.attributes` — and the round-trip test in `pkg/database/metadata_test.go` is what catches a field wired into three of them.
- **Model only what is honored**: a definition key gets a struct field only when something reads it. A parsed-but-ignored field reads as support that isn't there — `Response.Attribute`, `ErrorBlock.Path` and `Login.Cookies` were all removed for this reason, and `Captcha` is an empty struct because only the block's presence carries meaning. Verify a field is genuinely read by renaming it and checking that `go vet ./...` fails; the `unused` linter cannot see exported fields. The same applies to a status field that nothing sets, which is worse than unused because callers read a value that is always zero.
- **Definition-Driven Scraping**: Keep site-specific selectors and parsing rules in YAML definitions (`definitions/*.yml`) rather than hardcoding them in Go, so new indexers can be added without code changes.
- **No definitions are committed**: `definitions/` and `config/` are git-ignored, along with the database and the built binary. Definitions describe specific third-party sites, are third-party data owned by Jackett's project, and change on their own schedule; `config/` holds tracker credentials in plaintext and must never reach a commit. A missing definitions directory is therefore not an error — `DefinitionStore.Trackers` reports no definitions and `main.go` logs a startup warning naming the directory, since an empty install is the ordinary starting state rather than a fault. Tests must build whatever definitions they need inline (see `loadTestTracker`) and never depend on a file being present in `definitions/`.
- **Logging**: Use the single `*slog.Logger` constructed in `cmd/jacklet/main.go` and passed via constructor injection (`scraper.New`, `scraper.NewDefinitionStore`, `torznab.New`) — don't reach for the `log` package or a new logger instance. It's `slog.NewJSONHandler(os.Stdout, nil)`: structured JSON on stdout, not a log file — the standard shape (`time`/`level`/`msg` plus attributes) that container runtimes and log aggregators expect, letting the deployment environment own log routing/retention instead of Jacklet managing its own file.
- **The URL space is Jackett's, not Jacklet's own** (`Torznab.Routes`, `pkg/torznab/routes.go`, the single place every route is declared — `main.go` calls it, and so do the tests, so they exercise production routing): Torznab specifies query parameters and a response format but no URL layout, so there is no spec-blessed path to prefer, and Jackett's layout is what every client is configured with, since an operator sets one up by pasting a Jackett URL. Choosing anything else buys nothing and costs compatibility. One endpoint has no Jackett counterpart and is marked as Jacklet's own in `Routes`; everything else answers at the address Jackett serves it from. **A new endpoint goes where Jackett puts it, or is labelled as Jacklet's own where it is declared.**

  Jackett's CouchPotato-era surface is deliberately not served, and its absence is not an oversight to be corrected: no `/results/potato`, and the apikey is read from `apikey` alone, not from Jackett's `passkey` alias, which exists only for that same client. Every maintained Torznab client (Sonarr, Radarr, Lidarr, Readarr, Prowlarr) sends `apikey`. Jackett's indexer management and server-configuration routes are absent for a different reason: they act on a per-indexer configuration lifecycle Jacklet does not have, since a definition is a file in `definitions/` rather than something switched on, which is also why every indexer reports `configured` as true.
- **Per-indexer endpoints, plus one aggregate**: `GET /api/v2.0/indexers/{id}/results/torznab` serves exactly one tracker definition (matched by its YAML `id` field via `DefinitionStore.Find`). Jackett routes the torznab action as `[action]/{ignored?}`, so the trailing segment is optional and its value means nothing — clients send `api`, and `Routes` registers both forms. `GET /api/v2.0/indexers` lists every definition for discovery when configuring Sonarr/Radarr/Prowlarr. Per-indexer endpoints remain the recommended setup, since they let the client retry and disable each tracker on its own — the aggregate exists for clients that would rather add one URL.
- **The aggregate indexer (`torznab.AggregateID`, `"all"`)**: `/api/v2.0/indexers/all/results/torznab` and `/api/v2.0/indexers/all/results` answer from every configured definition. Both kinds of request are resolved by `Torznab.authorizedIndexer` into an `indexer` (see `pkg/torznab/aggregate.go`) holding one definition or all of them, and `handleCaps`/`handleSearch`/`Results` work in terms of that, so neither has to ask which kind it is serving — a new search-shaped endpoint should take an `*indexer` too rather than a `*scraper.Tracker`. An `indexer` standing for a set rather than for one definition sets `IsMeta`, which is what `t=indexers` answers for. Covering no definitions is **not** by itself an error. A meta indexer built when *nothing loaded at all* sets `IsUnconfigured` and answers 503, because that is a broken install; the aggregate and a filter expression both do, since the install is equally broken whichever one the client addressed, and a client that reaches this API by filter rather than by id would otherwise be the only kind never told. What makes the two cases separable is that `IsUnconfigured` is recorded at construction from the *loaded* set, not derived afterwards from `Defs` — deriving it would turn every filter that simply matched nothing back into a 503. **That 503 is a deliberate divergence** — Jackett assigns its aggregate `Indexers = _indexers.Values`, an empty collection rather than null, so its `IsConfigured` is true and it answers the same request 200 with empty arrays. An operator whose `definitions/` directory is empty would otherwise see nothing but successful, permanently empty searches; the cost is that a client reaching this API before definitions are in place sees a provider error rather than an empty result. A filter that matched none of the configured definitions, or a `Tracker[]` naming none of the ones addressed, is an ordinary empty answer — and `search` returns it without reaching the store, since `database.Search` reads an empty `Trackers` list as *every* tracker rather than none and would otherwise hand back the entire store. Four rules the implementation depends on, each with a test in `pkg/torznab/aggregate_test.go`:
  - **One store query, not one per tracker**: `database.Search.Trackers` is a list and `Torznab.search` passes `indexer.ids()`, so the sort order, the page and the total are global. Merging per-tracker pages in Go afterwards cannot reproduce a correct `offset`/`total`, so don't.
  - **A failing tracker must not fail the search**: `Torznab.scrape` fans out concurrently (bounded by `maxConcurrentScrapes`) and returns an error only when *every* definition failed; partial failures are logged. A single indexer's endpoint keeps the stricter behavior, where its own failure is the request's failure.
  - **`t=indexers` is the aggregate's own operation** (`handleIndexerList`, `pkg/torznab/indexerlist.go`): it lists the definitions behind the aggregate, each carrying its *own* caps rather than the merged set, since the point of the list is what each indexer can do alone. Jackett serves this for a meta indexer only and answers error 203 for any other, so a single definition gets that error document rather than a list of one. Note `indexerEntry`'s fields are in document order, not alphabetical — `encoding/xml` emits elements in field order, so sorting them would reshape the response.
  - **Download links belong to the owning indexer**: `rowIndexerID` uses the row's stored `tracker`, so a link reads `/api/v2.0/indexers/<owner>/download/<row>`. There is deliberately no `.../indexers/all/download/...` — the aggregate is a search surface, not a download one. The JSON results carry the owner in `TrackerId` for the same reason.
  - **A panicking tracker is a failed tracker**: `Torznab.scrape` wraps each fan-out goroutine in `scrapeGuarded`, so a panic becomes that tracker's error and the request answers like any other partial failure — a 502 naming the cause when no tracker answered and nothing is stored to fall back on. Those goroutines are not the request's, so nothing above them recovers; a single indexer's endpoint needs no guard, being the request goroutine `net/http` recovers itself.
  `AggregateID` shadows a definition that uses `all` as its own id; `warnIfNoDefinitions` says so at startup.
- **A panicking scrape is recorded as a failure**: extraction runs over whatever a tracker serves, so `ScrapeIndexer` recovers a panic into its own error return and the tracker fails the way an unreachable one does. That `defer` is registered after `finishScrape`'s, so it runs before it — the recovered failure has to be in the named return by the time the bookkeeping reads it, or the scrape is filed as a success, resetting the tracker's backoff, arming the de-duplication window for results that were never stored, and handing followers of the same search a nil error. The stack is logged rather than served, and recovery contains a panic rather than excusing one.
- **One indexer directory, in Jackett's shape**: `GET /api/v2.0/indexers` (`Torznab.JackettIndexers`) answers in Jackett's own JSON — a bare array, its lowercased and underscored keys, and capitalized `ID`/`Name` inside each capability — so a script written against Jackett enumerates Jacklet's indexers unmodified. The inconsistent casing is Jackett's; do not tidy it, since a tidier spelling is one a Jackett client would not find, and `pkg/torznab/jackettindexers_test.go` asserts the wire bytes rather than round-tripping through the struct for exactly that reason. Fields Jacklet has no equivalent for (`last_error`, `potatoenabled`, `tags`) are sent as empty values, never omitted or null: Jackett always sends a value, and a nil Go slice marshals to `null`. `configured` is always true, because a definition is in `definitions/` or it is not — there is no step that turns one on — and Jackett's `?configured=true` filter is accepted and ignored for the same reason. The aggregate indexer is deliberately absent, or a client walking the list to add every indexer would add all of them twice. This is the only indexer listing: search modes and categories are in an indexer's caps document and parse errors are logged as definitions are read and shown in the admin panel when one is configured, so a second listing shape would be one more thing to keep in sync for data already served.
- **Indexer filters stand in for an indexer id** (`pkg/torznab/indexerfilter.go`): `status:healthy`, `!type:private+lang:en`. Jackett resolves the same expressions at the same position in the path, and a client offering its user "all working indexers" rather than a list of them sends one, so the expression has to resolve here for that client to search at all. A colon is what marks an id as an expression — no definition id contains one. Two rules the implementation depends on. **Health is a deliberate divergence**: Jackett's `IsHealthy` is `errorCount == 0 && expireAt > now`, a validity window opened by a search that succeeded, so an indexer Jackett has not searched yet is *unknown* and `status:healthy` answers a freshly started instance with nothing — which would leave a client that offers only "all working indexers" unable to search until something else had searched first. Health here is the absence of a recorded failure instead, so a tracker nothing has scraped yet is healthy. Don't "fix" this back to parity without solving the cold-start case. (Jackett's `test:` filter *is* last-error based, `LastError == null`; Jacklet has no separate test action, so both names read the one state it keeps.) Second, an expression naming a filter Jacklet does not serve is a 404 rather than an empty match, since a client cannot tell "no indexer is healthy" from "I asked for something you ignored". Jackett has no answer to copy here: `GetWebIndexer` throws `Unknown indexer` for a name that parses as no filter, and nothing on the request path catches it, so the 404 with a JSON body is Jacklet's own. `tag:` is the one exception it answers empty for, because a definition is a file in a directory with nothing to hang a user's label on.

- **JSON results endpoint alongside the XML one**: `GET /api/v2.0/indexers/{id}/results` runs the exact same scrape-then-search pipeline as `GET /api/v2.0/indexers/{id}/results/torznab/api?t=search` (same params: `q`, `cat`, `season`, `ep`, `imdbid`, `tvdbid`, `limit`, `offset`) but returns JSON — Jackett's own address and Jackett's own idea, a convenience it layers on top of the Torznab spec (which is XML-only) rather than something the spec itself defines. `handleSearch` (XML) and `Results` (JSON) share `searchParamsFromQuery` and `search`/`toTorznabItem` — a schema/behavior change to the search pipeline (new param, different scrape error handling, etc.) belongs in the shared code, not duplicated into just one of the two handlers.
  - **The response is Jackett's `ManualSearchResult`, key for key** (`searchResults`, `searchIndexer`, `jackettResult` in `pkg/torznab/results.go`). Torznab is XML-only and defines no JSON variant, so there is no spec to follow here and nothing to gain from a shape of Jacklet's own: a client reaching this address is one written against Jackett and reads those keys literally. That is why they are PascalCase, why `Peers` carries the leecher count (Jackett subtracts the seeders before serializing it), why `Category` is a list, and why `Details` is emitted twice, also under the older `Comments` name — the one key here Jackett itself does not send.
  - **Nullable numbers read zero as absent.** Jackett's `ReleaseInfo` declares most of its counts `long?`/`double?` and sends null for a field a definition did not scrape. The store holds plain numbers, so zero is the only signal of absence available, and `optional` in `pkg/torznab/results.go` turns it into null — the same reading `attributes` already takes for the Torznab feed, where such a field is left out rather than emitted as 0. `Seeders`, `Peers`, `DownloadVolumeFactor` and `UploadVolumeFactor` are exempt and always numbers: zero is an answer for each (an empty swarm, a freeleech), and the scraper defaults both factors to Cardigann's 1, so neither is ever unset. Don't extend `optional` to them — reporting null there would lose the common case to describe the rare one. Making the rest genuinely distinguishable would mean nullable columns in the store, which is a schema change rather than a rendering one.
  - **Three places it must not follow the XML feed.** It accepts the parameter names Jackett binds there (`Query`, `Category`/`Category[]`, `rageid`, `Tracker[]`, matched case-insensitively and with the brackets stripped — see `searchQuery`), since a client written against Jackett sends those and a search that ignored them would answer with unrelated latest releases rather than with nothing. Jackett's `ApiSearch` is the whole list of what it binds at that address: it reads neither `q` nor `cat` there, so those are Jacklet's addition rather than Jackett's. It answers unpaged (`jsonLimits`), since `ApiSearch` has no limit or offset at all. And an unreachable tracker is a 200 with the failure recorded against that indexer in `Indexers[]`, not a 502 — the shape has somewhere to put it, and a request covering several indexers must not lose the ones that answered. The XML feed keeps the 502 because an RSS document has nowhere to report a failed indexer.
  - **The spec's two search endpoints no longer document one list.** `jsonOnlyParams` in `pkg/torznab/openapi_test.go` names the ones only the JSON endpoint takes, and each is there because Jackett itself binds it only at that address. The parameter tests walk both paths for the same reason.
- **A torrent file and a magnet are separate columns**: a tracker commonly offers both, and Cardigann declares them as separate fields, so `torrents.magnet` sits beside `download_url` and the panel gives each its own column. `download` naming a magnet is stored as one, leaving `download_url` empty, since there is nothing to fetch through the tracker's session. An info hash alone becomes a magnet only for a definition whose `type` is `public` or `semi-private` (`isPubliclyShared`): such a link names no trackers, so a client reaches peers only through the DHT, which a private tracker's torrents are deliberately absent from, and it carries no passkey. Jackett applies the same restriction. **The built link is trackerless, which Jackett's is not**: its `MagnetUtil.InfoHashToPublicMagnet` appends a fixed list of ten public `tr=` announce URLs, so a client resolves it faster than through the DHT alone. Carrying that list would mean shipping third-party announce addresses that go stale and that every built magnet then advertises, which is the reason to leave it out rather than an oversight — but the cost is real and it is a divergence, not parity. The reverse direction, reading an info hash back out of a magnet (`magnetInfoHash`), has no such restriction: a hash taken from a link already in hand discloses nothing the link did not. Torznab advertises the magnet as the `magneturl` attribute (and `MagnetUri` in the JSON results) while `link` stays the proxied torrent file, so a client picks; a row with no torrent file has the magnet as its `link`, and its download endpoint redirects to it rather than fetching.
- **Downloads are proxied, not handed off**: `GET /api/v2.0/indexers/{id}/download/{row}` (`Torznab.Download`) — Jacklet's own path, because Jackett serves the equivalent from `/dl/{indexerId}` keyed by an encrypted `path` parameter carrying the tracker's link, a payload only Jackett can mint; a client never builds this address anyway, it follows the one in the feed. It fetches the `.torrent` from the tracker using Jacklet's own authenticated session and serves it as `application/x-bittorrent`. The admin panel's result tables link to `GET /admin/indexers/{id}/download/{row}` (`Admin.handleDownload`) for the same reason; both resolve the row and then hand it to `torznab.ServeTorrent`, which decides nothing about who may ask — the Torznab endpoint checks `JACKLET_API_KEY`, the panel checks its session. A magnet is redirected rather than fetched, since the client resolves one itself, which is why `downloadPath` leaves it out of the panel's proxy links. A Torznab client has no account on a private tracker, so giving it the tracker's own link returns a 403 or a login page saved as a `.torrent`. `{row}` is the store's row id rather than a URL, so the endpoint resolves what to fetch from the database and cannot be pointed at an arbitrary address. The fetched body is capped at `defaultMaxDownloadBytes` (1 MiB) — a `.torrent` is a piece-hash list, well under a megabyte even for a large release, and without a cap a tracker or a compromised mirror could push arbitrary volume through the proxy to its clients. Unlike a scrape, exceeding it cannot fail the request: `ServeTorrent` streams the body straight out, so the headers are already sent and the only options left are to truncate and log.
- `pkg/admin`: the web administration panel (`/admin`), server-rendered with `html/template` from templates embedded in the package.
- **The panel is off unless a password is set**: `admin.New` takes an `*admin.Password` built from `JACKLET_ADMIN_PASSWORD`/`JACKLET_ADMIN_PASSWORD_HASH`, and `Enabled` reports false when neither is set; `main.go` registers no `/admin` routes in that case, so every path 404s. The panel reads and writes tracker credentials, so "no password configured" must mean "no panel", never "an open panel".
- **Prefer a hashed admin password**: `JACKLET_ADMIN_PASSWORD_HASH` holds a PBKDF2-HMAC-SHA256 hash (`pbkdf2-sha256$<iterations>$<salt>$<key>`, stdlib `crypto/pbkdf2` — no new dependency), generated by `jacklet hash-password`, and takes precedence over the plaintext `JACKLET_ADMIN_PASSWORD`. The hash records its own iteration count so raising `hashIterations` doesn't invalidate hashes already deployed. A malformed hash fails startup rather than falling back: quietly ignoring it would leave the panel accepting a different password, or none. `hash-password` reads from stdin, never from an argument, since arguments are visible to every process on the machine. Hashing does not protect the plaintext path — the value is in the process environment either way — it protects against the password being disclosed in a compose file, a unit file, or a pasted bug report.
- **The panel authenticates with sessions, not `JACKLET_API_KEY`**: `pkg/admin/session.go` issues a random 256-bit token in an `HttpOnly`, `SameSite=Lax` cookie scoped to `/admin`. It is `Secure` when the request arrived over TLS or when an HTTPS `JACKLET_BASE_URL` says a reverse proxy terminates TLS; leaving that setting empty preserves plain-HTTP deployments. `guard` requires a session for every route and a matching CSRF token for every non-GET. A request whose token has no session — aged out past `sessionLifetime`/`sessionIdleTimeout`, or held over a restart, since the store is in memory — has its cookie cleared and is sent to `/admin/login` with a 303, which the browser follows with a GET whatever method it started as. A GET carries its path along as `?next=`, so signing in returns to the page that was asked for; `safeNext` admits only a path inside `adminPrefix`, cleaned in its decoded form, since an escaped `%2e%2e` survives `path.Clean` untouched while still walking a directory up in the browser. A non-GET carries nothing, because a browser following a redirect can only ask for a page again with a GET. `JACKLET_API_KEY` travels in a query string, which is fine for a machine API and unacceptable for a UI holding tracker passwords — don't merge the two.
- **A state-changing operation is a POST**: the manual search scrapes the tracker live, so it is `POST /admin/search` with a CSRF token rather than a bookmarkable GET. `SameSite=Lax` still sends the session cookie on a top-level GET navigation, so a side-effecting GET would be reachable from another site.
- **Secrets are never rendered into a page**: `settingViews` substitutes `maskedSecret` for any stored credential (`isSecret` matches type `password` and names containing password/passkey/apikey/cookie/token/secret), and `handleSaveSettings` treats the mask submitted back as "keep what is stored". Rendering the real value would put tracker passwords in the DOM, in browser history, and in any page cache.
- **Config writes are atomic and owner-only**: `ConfigStore.Save` writes a temp file with mode 0600 and renames it into place, because the file holds credentials and a scrape may be reading it concurrently. Saving also invalidates the cached login for that tracker, since the credentials it was established with may have just changed.
- **Configuration resolves flag, then environment, then default**: `parseSettings` (`cmd/jacklet/flags.go`) gives each flag the matching environment variable as its default, which is where that precedence comes from. `run` works from the resolved `settings`. Each setting carries both spellings: `-base-url`/`JACKLET_BASE_URL`, `-port`/`JACKLET_PORT`, `-flaresolverr-url`/`JACKLET_FLARESOLVERR_URL`, `-definitions-dir`/`JACKLET_DEFINITIONS_DIR`, `-config-dir`/`JACKLET_CONFIG_DIR`, `-contact-email`/`JACKLET_CONTACT_EMAIL`, `-db-path`/`JACKLET_DB_PATH` and `-retention-days`/`JACKLET_RETENTION_DAYS`. An invalid public URL, contact email, port or retention count fails startup, so a typo in a deployment is visible immediately.
- **Credentials have no flag, and can come from a file**: `JACKLET_API_KEY`, `JACKLET_ADMIN_PASSWORD` and `JACKLET_ADMIN_PASSWORD_HASH` are environment-only, listed in `secretEnvOnly` and printed under their own heading by `printUsage`. An argument is readable by every other process on the machine for as long as the server runs, and is kept in shell history — the same reasoning that keeps `jacklet hash-password` reading from stdin. Each also reads a `_FILE` variant (`environment.secret`) naming a file to take the value from, which is how Docker and Kubernetes deliver a secret and keeps it out of the environment, where child processes and `docker inspect` can reach it. Supplying both a credential and its `_FILE` form is an error: ignoring one of two deliberately supplied values is how the wrong password reaches production. A trailing newline is stripped because a file written by `echo` has one; other whitespace is kept, since it may be part of the value. An unset `JACKLET_API_KEY` leaves the indexer endpoints unauthenticated, and logs a startup warning.
- **Environment variables are namespaced**: `environment.get` (`cmd/jacklet/env.go`) reads `JACKLET_<NAME>`. A shared environment is a shared namespace — several services in one compose file, or one `EnvironmentFile=` — so an unprefixed `API_KEY` or `DB_PATH` is liable to be another program's, and a collision on `ADMIN_PASSWORD` silently changes who can sign in.
- **`openapi.yaml` is ordered, like the Go structs**: `paths`, the `components` sections, the entries within each of them, and each schema's `properties` are sorted alphabetically. These are lookup tables — nobody reads `components/parameters` top to bottom — so alphabetical is what makes an entry findable, and it is where a newly added parameter belongs rather than appended at the end. Each schema's `required` is the sorted list of its own properties, which doubles as the check that catches a field added to a Go struct but left out of the spec: every field of `jackettIndexer`, `jackettCapability`, `searchResults`, `searchIndexer` and `jackettResult` is emitted unconditionally, so `required` and `properties` must match exactly.
- **Three failure formats, one per endpoint kind** (`pkg/torznab/errors.go`): the Torznab XML endpoint answers with `<error code description/>`, the JSON endpoints with `{"error": …}`, and a download with a bare status, since a `.torrent` is no document the client was going to parse. The shared pipeline (`authorizedIndexer`, `findAuthorizedTracker`, `search`) does not choose: each entry point passes its own `errorWriter`, and every one of them takes the Torznab code even though only the XML writer renders it, because the code describes the failure and not the rendering. **A new failure path takes the `errorWriter` it was handed rather than reaching for `http.Error`**, or the endpoint silently answers in a format its client does not parse. The codes are Jackett's own, from its `RequiresApiKey`/`RequiresConfiguredIndexer` filters and the torznab action: 100 rejected key, 201 unknown indexer, 203 function not available, 900 catch-all — plus 202 for an unknown `t`, which is Newznab's, since Jackett treats anything it does not recognize as a search. Jacklet keeps its own status codes (502 for an unreachable tracker, where Jackett sends 400), because the status describes the failure more precisely and the client branches on the code.
- **The spec is tested, not just described**: `pkg/torznab/openapi_test.go` parses `cmd/jacklet/public/openapi.yaml` (as a `yaml.Node`, so key order survives) and fails on drift — an undocumented struct field, a `required` list that no longer matches its properties, a component nothing references any more, a `$ref` that names nothing the document defines, a parameter documented on the XML search endpoint but not the JSON one, and either ordering rule broken. It also reaches past the spec into the handler, in both directions, since the rest of the tests compare the spec against itself: every documented query parameter is sent through `searchParamsFromQuery` and has to arrive in the `scraper.SearchParams` field named for it in `searchParamFields` — naming the field is what catches two parameters wired to each other's, where checking only that the value arrived somewhere would not — and every `q.Get` in that function is read back out of the source and must be a parameter the spec documents, so a name the handler starts reading cannot go undocumented either. It lives in this package because it is the only one that can see both the spec and the response structs, which stay unexported. Adding a response field or a query parameter means updating the spec in the same change; the test says so rather than leaving it to a reviewer.
- **…but an operation's `parameters:` list is grouped, not sorted**: Scalar renders parameters in document order, so that list is the order a human configuring Sonarr/Radarr reads. It is grouped by what a parameter is for — the indexer and the operation (`id`, `row`, `t`), the core search (`q`, `cat`), television (`season`, `ep`), the identifiers a tracker may be searched by directly, `extended`/`year`/`genre`, music, books, then paging (`limit`, `offset`) — and a new parameter goes into its group. Sorting it alphabetically scatters the pairs (`season` away from `ep`, `limit` away from `offset`) and opens the list with `album`, ahead of `q`. This is the same exemption `torznab.Channel` and `torznab.Item` take, where declaration order is the wire format; here it is the rendered format. The document's own top-level keys are exempt too, keeping the conventional `openapi`/`info`/`servers`/`security`/`paths`/`components` reading order.
- **API docs**: `cmd/jacklet/public/openapi.yaml` describes Jacklet's own HTTP surface (`/api/v2.0/indexers`, `/api/v2.0/indexers/{id}/results/torznab/api`, `/api/v2.0/indexers/{id}/results`) — it documents what Jacklet exposes, not the Torznab protocol itself (which has no OpenAPI spec of its own). `GET /docs` serves `cmd/jacklet/public/docs.html`, a Scalar API-reference page pointed at that spec via CDN script (`https://cdn.jsdelivr.net/npm/@scalar/api-reference`) — no build step, no bundled JS in the repo. Both files are compiled in with `//go:embed public` and served from an `fs.Sub`, so the binary is genuinely self-contained and doesn't require its working directory to be the source tree. When adding or changing an endpoint (new query param, new response field, new route), update `openapi.yaml` in the same change so the docs don't silently drift from the actual handlers. The `/admin` panel is deliberately absent from it: the spec describes the machine API that Sonarr/Radarr/Prowlarr consume, and the panel serves HTML pages to a human, not a documented API surface.
- **One shared, long-lived `Scraper`**: `main.go` constructs exactly one `scraper.Scraper` and passes it into `torznab.New` — don't construct a fresh `Scraper` per request. It's safe for concurrent use and holds state that must persist across requests to be useful: the HTTP client's cookie jar (session cookies from one request are available to the next), the cached FlareSolverr session (`flareSolverrSession`, reused instead of re-solving a challenge every search), and per-tracker rate-limit/backoff bookkeeping (`scrapeState`, `planScrape`/`recordScrapeOutcome`). `main.go` calls `scrpr.Close(ctx)` on graceful shutdown (`SIGINT`/`SIGTERM` via `signal.NotifyContext`) to destroy that FlareSolverr session rather than leaking it server-side.
- **Rate limiting with backoff**: a request for the same indexer within `minScrapeInterval` (5s) is served from whatever's already in the database instead of re-scraping. A failed scrape additionally backs off exponentially (`minScrapeInterval * 2^failures`, capped at `maxScrapeBackoff` = 10m) so a persistently broken tracker isn't hit every 5s forever; a success resets the failure count.
- **Config overrides**: `JACKLET_CONFIG_DIR/<tracker-id>.yml` (default dir `config`, missing file is not an error) is a flat `setting-name: value` YAML map layered over a definition's own `settings:` defaults — see `scraper.ConfigStore` in `pkg/scraper/config.go`, which both the scraper and the admin panel hold. Writing overrides may change credentials, so a caller that holds a `Scraper` must follow `ConfigStore.Save` with `Scraper.InvalidateLogin`. This is the only way to change a `.Config.*` value Jacklet currently has; there's no runtime/API-driven config mechanism.
- **A search path may declare the categories it serves**: `SearchPath.selectCategories` skips a path with no category in common with the search, and narrows that path's own `.Categories` to the ones they share — so a definition keeping movies on one page and music on another fetches one page per search rather than both. A path declaring none always runs, over all of them. Two things follow from it:
  - **A search naming no category falls back to `DefaultCategoryIDs`**, the mappings marked `default: true`, exactly as Jackett does. Without that fallback an unfiltered search would share no category with any declared path and fetch nothing at all. Most definitions mark none, and then `.Categories` stays empty — which is what a definition's `{{ if .Categories }}...{{ else }}` branch is written for, so don't "fix" the empty case by substituting every category.
  - **Every path being skipped is not a failure.** `scrapeMirror` reports such a mirror as reachable: it was never asked anything, so failing over would ask the next mirror the same question and skip the same paths, and reporting the tracker as down would turn "this search matches no page of this site" into an error the client sees.
  - One Jackett quirk is replicated rather than improved on: a *negated* path (`categories: ["!", 401]`) that does run gets an **empty** `.Categories`, because Jackett computes the same intersection in both branches and the one it just found empty stays empty. A definition using the negated form would have been written against Jackett's reading, and matching the quirk is what lets it work here unmodified — which is the compatibility the project exists for.
- **A search does not follow redirects unless its path says to** (`SearchPath.FollowRedirect`): `fetch` picks `noRedirectClient` by default and `httpClient` when the path sets `followredirect: true`. This is Cardigann's default and the reason for it is worth keeping in mind — a tracker whose session has lapsed answers a search by redirecting to its login page, and following that scrapes the login page as if it were results, turning a lapsed session into a silent "no matches". Whatever the 3xx carries is parsed instead, which for a bare redirect is nothing. The two clients **share one cookie jar**, so a session established by the login flow is still sent; a second `http.Client` that quietly had its own jar would log every scrape out.
  - Note the name is used twice in the Cardigann format. Inside a search path it is this. At the **top level** of a definition it is a different setting, which in Jackett rewrites the configured site URL when a login test is redirected elsewhere; Jacklet does not implement that and always follows a redirect during login, since it answers a moved site with mirror failover rather than by editing an operator's configuration.
- **An empty response body is an answer, not an outage**: `charset.NewReader` reports an empty read as `io.EOF`, which `fetch` turns into an empty string rather than passing on. Left as an error it becomes "all links unreachable" — mirror failover, and a 502 to a client that should have been told "no results". An unfollowed redirect is the common case, but a tracker answering 204, or 200 with nothing, is the same thing.
- **One YAML escape is repaired before decoding** (`pkg/scraper/yamlcompat.go`, `unmarshalYAML`, used for definitions *and* config overrides so a regex in a double-quoted scalar is not refused in one file and accepted in the other): YAML 1.2 lists `\/` among the escapes a double-quoted scalar may use, and `gopkg.in/yaml.v3` — libyaml-derived, so YAML 1.1 — is the only parser in play that rejects it. It is the *only* YAML 1.2 escape it rejects, which is what keeps the repair this narrow. Every definition in Jackett's repository is expected to parse here, and one writing that escape is unusable for no other reason without the repair. `unmarshalDefinition` runs `repairSlashEscapes` **only after a plain decode has already failed**, and keeps its result only if that then succeeds, so nothing that parses today can be changed by it; a failure is reported as the original error, which describes the file the operator wrote. The scanner has to know when it is inside a double-quoted scalar, and `opensScalar` is the subtle part: `:`, `-` and `?` are YAML indicators only when a blank follows them, so the closing quote of a plain scalar like `selector: td a[href*="/torrent-category-"]` must not be read as opening one — getting that wrong leaves every later line of the file inside a scalar that was never opened, which is exactly the bug an earlier version of it had.
- **A response is bounded, because nothing else bounds it** (`defaultMaxResponseBytes`, 32 MiB, held on the `Scraper` so a test can lower it): the HTTP client's timeout bounds how *long* a response may take, not how large it may be, and `fetch` reads the whole body into memory and then builds a document tree on top of it. The aggregate indexer makes that concurrent across as many trackers as `maxConcurrentScrapes` allows. The same cap covers the FlareSolverr reply, which carries the rendered page as JSON and is the same exposure by another route. Exceeding it **fails the scrape** rather than truncating: half a document parses into plausible-looking nonsense, which is worse than an error that says what happened. A real listing page is tens of kilobytes, so the cap is invisible in normal use — raise it rather than removing it if some tracker ever needs more.
- **Link fallback**: `ScrapeIndexer` tries `Links` then `LegacyLinks` in order (`candidateBaseURLs`), stopping at the first one where at least one search path's fetch succeeds. A mirror that connects but returns zero matching rows is not a failure — don't reinterpret "no results" as "try the next mirror." A row's relative download/details URLs are resolved against **the search page that served it** (`storeRows` threads `searchURL` into `torrentFrom`), as a browser resolves them: a definition whose search path sits in a subdirectory, such as `forum/tracker.php`, carries row links relative to that directory, and resolving them against the site root addresses a page that does not exist — never against `def.Links[0]`, which points at the dead primary after a failover and panics outright on a definition that declares only `legacylinks`.
- **A failed scrape falls back to the store, it doesn't fail the request**: `handleSearch` and `Results` both run `search` before deciding what a scrape error means, and return 502 only when there is also nothing stored for that indexer. The store exists so a tracker outage degrades to stale results rather than to none; `openapi.yaml` documents that contract.
- **`t=` query parameter values, not the caps XML element names**: Sonarr sends `t=tvsearch`, Radarr sends `t=movie` — the *unhyphenated* Newznab/Torznab spec values — not `tv-search`/`movie-search`, which only exist as XML element names inside the caps response (`<tv-search>`, `<movie-search>`). `ServeHTTP`'s switch accepts both forms defensively; don't "clean up" it back down to just the hyphenated ones, since that reintroduces a real bug that breaks TV/movie search against real Sonarr/Radarr while still looking fine against anything that queries with `t=search`.
- **Pagination**: `searchParamsFromQuery` reads `limit` (default 50, capped at `maxLimit`=100) and `offset` from the query string; `Store.Search` applies them via SQL `LIMIT`/`OFFSET` and reports the full match count across all pages (a separate `COUNT(*)` query) as `total`, not just the current page's row count. Keep `defaultLimit`/`maxLimit` in sync with the values advertised in `torznab.Limits` in `handleCaps`.
- **Definitions reach the handlers through an interface**: `torznab.New` takes a `scraper.TrackerSource` (`Find`, `Trackers`), not a directory path, so a program embedding `pkg/torznab` can serve definitions from a database, a remote service, or memory instead of YAML files on disk — `pkg/` is a library surface, and the directory layout shouldn't be baked into the handler. `main.go` injects a `DefinitionStore`. An implementation must be safe for concurrent use and must not hand back a `Tracker` aliasing state it later mutates.
- **Definitions are cached, not re-parsed per request**: `DefinitionStore` (`pkg/scraper/store.go`) holds the parsed definitions and re-reads a file only when its size or modification time changes, so a file added, edited, or removed still takes effect on the next lookup without a restart. `torznab.New` builds one and every handler goes through it. Caching is what makes a Jackett-sized directory viable: parsing every file on every request costs time and allocations in proportion to the directory, and the project exists to serve directories of several hundred definitions. `Find` copies only the definition it matched rather than materializing the whole directory, since it runs on every search.
- **A broken edit doesn't take an indexer off the air**: a definition that parsed before and fails to parse now keeps serving its last good version, with the failure reported alongside it in `Trackers`. Without this, saving a syntax error mid-edit would 404 a live indexer until it was noticed.
- **Broken definitions are surfaced, not just skipped**: `DefinitionStore.Trackers` returns `(trackers, []DefinitionError, error)` — a file that fails to read/parse is skipped and reported in the `DefinitionError` slice rather than aborting the whole directory load. `DefinitionStore` logs each one as it reads it (`pkg/scraper/store.go`, "failed to parse definition file", with the path and the error), and the admin panel lists them under "Definition errors" when one is configured, so a broken YAML file doesn't just silently vanish. The log is the only surface on a headless install, which is why the reporting lives in the store rather than in a handler. The Torznab API does not report them: Jackett's indexer array has nowhere to put them.
- **Always resolve an indexer's id via `scraper.TrackerID(def)`, never `def.ID` directly**: a definition may omit `id` (`TrackerID` falls back to `name`); `DefinitionStore.Find` and the DB queries already account for this. Every place that surfaces an indexer's identity to a caller (`JackettIndexers`, `Results`, error messages) must use the same fallback, or a definition without an explicit `id` is advertised with an empty id, and a client built from the listing asks for a broken `/api/v2.0/indexers//results/torznab`-style path even though the indexer is perfectly reachable by name.
- **HTTP server hardening**: `main.go`'s `http.Server` sets `ReadTimeout`, `IdleTimeout`, and `ReadHeaderTimeout` in addition to `WriteTimeout` — the last one is deliberately `torznab.ScrapeTimeout + 15s`, not some smaller generic default, since a legitimate slow-but-working search can take up to `ScrapeTimeout` before it has anything to write. If `ScrapeTimeout` ever changes, `WriteTimeout` must move with it.
- **`GET /healthz`**: liveness/readiness probe (pings the database, 200/503) for container/orchestrator health checks — see `healthCheck` in `main.go`.
- **`GET /{$}` redirects to `/docs`**: the exact root path only (Go 1.22 `{$}` pattern), so `public/`'s lack of an `index.html` doesn't turn `GET /` into a raw directory listing; every other static path (e.g. `/openapi.yaml`) still falls through to the `http.FileServer` catch-all.

### Cardigann template engine

Real Jackett/Cardigann definitions use a small templating language (`{{ .Result.x }}`, `{{ .Config.x }}`, `{{ .Keywords }}`, `{{ .Categories }}`, `{{ if }}...{{ end }}`, `{{ range }}...{{ end }}`) inside `search.inputs`, field `text`, and filter `args`. Cardigann's syntax was deliberately modeled on Go's own `text/template`, so `pkg/scraper/filters.go`'s `renderTemplate` reuses `text/template` directly against a `templateData` context, rather than a bespoke parser — this gives `{{ if }}`, `{{ range }}`, `and`/`or`/`ne`/etc. for free.

- **Cardigann's two template functions, `join` and `re_replace`**, are supplied as a `template.FuncMap` (`cardigannFuncs`). `join` concatenates a list variable, in practice always `.Categories`; `re_replace` is the same substitution as the filter of that name. An invalid pattern is returned as an error rather than swallowed, since the alternative is sending the tracker a value the definition meant to rewrite.
- **`rewriteCardigannTemplate` is the one place reusing `text/template` costs something, and it is load-bearing.** Jackett applies templates by substituting over the text with a regex, so it never parses them — which lets its definitions carry two shapes a real parser rejects outright. Both are rewritten before `Parse`, and without either the template fails and the literal `{{ ... }}` is sent to the tracker, so don't "simplify" this away:
  - **A regular expression argument.** Go lexes a template's string literals by Go's rules, where `"\s"` is not an escape but a parse error, and `{{ re_replace .Keywords "[\s]+" "%" }}` is the most common use of that function in Jackett's definitions. Each backslash that does not begin a valid Go escape (`goStringEscapes`) is doubled.
  - **A hyphenated setting name.** `{{ .Config.cat-id }}` parses as a subtraction, so it becomes `(index .Config "cat-id")` (`hyphenatedMapKey`). Only `.Config` and `.Result` are rewritten, because only those two are maps; and a hyphen can never be an operator here, since the template language has no infix arithmetic.
  - Each rewrite is confined to where it applies: escaping only inside a quoted argument, the key rewrite only outside one, and neither touches the text between actions.

- `.Config.<name>` comes from a definition's `settings:` block (`pkg/scraper/definitions.go`'s `Setting`/`defaultConfig`), layered over by `JACKLET_CONFIG_DIR` overrides and the admin panel. Every value is a **string**, including a checkbox, which takes `cardigannTrue` (`"True"`) or `cardigannFalse` (`""`) — Jackett's own two values. Don't "improve" a checkbox back into a Go `bool`: `{{ if .Config.x }}` reads either correctly, but `{{ if eq .Config.x .False }}` is a shape real definitions use, and Go's template `eq` refuses to compare a `bool` against the empty string `.False` holds, failing the whole expression rather than just that comparison.
- `.Config.sitelink` is supplied by Jacklet rather than declared by a definition (`withSiteLink`), matching Jackett, which sets it for every indexer — definitions routinely build absolute URLs out of it, so without it they yield broken download and details links. It names **the mirror that answered**, not `Links[0]`, for the same reason row URLs resolve against the search page: after a failover the first link is the host that just failed. A definition that declares a `sitelink` setting of its own keeps whatever the operator configured.
- `.True` and `.False` are Cardigann's boolean literals, `"True"` and `""`. `.False` is empty rather than `"False"` because definitions compare *unset* values against it (`{{ if eq .Query.IMDBID .False }}`), and because that is also what `{{ if }}` reads as false.
- `.Categories` is the requesting client's standard Torznab category IDs (e.g. `?cat=2000`), reverse-mapped through `caps.categorymappings` to this tracker's own site-specific category IDs (`siteCategoryIDs` in `pkg/scraper/categories.go`). `standardCategoryIDs` mirrors Jackett's full standard category list, including subcategories (`Movies/HD` = 2040, `TV/HD` = 5040, ...) — a name missing from it collapses to `Other` *and* vanishes from that indexer's caps, so keep it complete rather than trimming it to whatever the bundled definitions happen to use. A request for a top-level category expands to its subcategories (`ExpandCategoryIDs`), both when selecting the tracker's own categories and in the SQL `category IN (...)` filter, matching how Jackett treats a parent category as meaning the whole tree.
- `.Query.*` is the raw Torznab request, built by `SearchParams.templateQuery`. The field set of `queryParams` deliberately matches the one Jackett's `CardigannIndexer` builds, because Go's `text/template` treats a *missing* field as an error and `renderTemplate` answers an error by leaving the string unresolved — a definition referencing a variable Jacklet lacks would therefore send the tracker a literal `{{ .Query.IsTVSearch }}` rather than nothing. When adding a Torznab parameter, add it to `queryParams` too. Four things to know:
  - `.Query.Type` is the search mode, normalized by `canonicalSearchType` to the unhyphenated spec form (`search`, `tvsearch`, `movie`, `music`, `book`). `ServeHTTP` accepts every spelling real clients send, so definitions must not have to. The `Is*` flags (`IsTVSearch`, `IsRssSearch`, `IsIdSearch`, ...) are derived from it and the other parameters, and are `"True"` or empty so they read as booleans in `{{ if }}`.
  - `.Query.Categories` is what the **client** asked for — standard Torznab ids — while the top-level `.Categories` is the tracker's own ids, reverse-mapped through `caps.categorymappings`. Jackett draws the same line, and a definition building a request out of site categories wants the top-level one. Don't collapse the two.
  - `.Query.Q` is the raw `q`, unlike `.Keywords`. `.Query.Episode` is the `SxxEyy` string; `.Query.IMDBIDShort` drops the `tt`. `.Query.Series` and `.Query.Movie` are always empty, as they are in Jackett.
  - `.Query.Keywords` and the top-level `.Keywords` are the same text before and after the definition's `keywordsfilters` run — `SearchParams.keywords` produces one, `applyFilters` the other, exactly as Jackett derives `.Keywords` from `.Query.Keywords`. A definition that has rewritten the terms for its own search box reaches for `.Query.Keywords` when it still needs what the client actually sent.
  - `.Query.APIKey` is deliberately **absent**, on the same reasoning as `.Env`: it is Jacklet's own `JACKLET_API_KEY`, and a third-party YAML definition must not be able to put it in a tracker request.
- **Paging is the definition's job, not a loop in Jacklet**: Cardigann has no multi-page scrape loop, in Jackett either — `CardigannIndexer` iterates `search.paths` exactly once each, as `scrapeMirror` does. A definition that pages does it by building the request from `.Query.Offset`/`.Query.Limit`, or by declaring several `paths` entries with different page inputs. Don't add a page loop: it would be a behavior no definition is written against. What Jacklet does add is `pagesServerSide`, which detects a definition referencing those two variables and appends `SearchParams.pagingKey` to the de-duplication key, so asking for page 2 right after page 1 reaches the tracker instead of being answered from page 1's scrape. For every other definition the key is unchanged, since two pages of one search are then the same tracker request and re-issuing it would be a request the tracker did not need to serve.
- `.Keywords` is `SearchParams.Query` with season/episode folded in as "SxxEyy" (`SearchParams.keywords`) before `keywordsfilters` run — matching how Jackett feeds tv-search queries to Cardigann trackers that lack dedicated season/episode inputs, and why such definitions declare `keywordsfilters` that rewrite "S01E02"-shaped text in the query.
- `.Today` is `todayVars`: `{{ .Today }}` renders the current date (`2006-01-02`, a Jacklet addition) via its `String` method, and `{{ .Today.Year }}` is Jackett's own variable. `.Today.Year` is the **previous** year during January, as it is in Jackett — definitions reach for it to complete a date a tracker prints without one, and in January such a listing is far likelier to be from December than from the last few days. `.Env` is deliberately **not** implemented — exposing the process environment to arbitrary, possibly third-party YAML definitions would let a definition exfiltrate a secret (e.g. `JACKLET_API_KEY`) into a scraped field that then gets stored and re-served over the Torznab API. Don't add `.Env` without a real access-control story for definitions first.
- `.Result.<field>` is the row's already-extracted field values. `Search.Fields` is a `FieldList` (not a plain map) specifically to preserve YAML declaration order, since a field or filter may reference an earlier field — order must match the definition author's intent, not Go's random map iteration.
- Filters live in `filterRegistry` (`pkg/scraper/filters.go`), which maps a definition's filter name to a small function plus the argument count it accepts. Add a filter by adding an entry and a function; `applyFilter` checks arity once from the entry rather than each filter re-checking `len(args)`. A name absent from the registry is reported as unsupported rather than silently skipped, and a filter whose entry sets `maxArgs: -1` ignores surplus arguments — several always did, and definitions rely on it.
- Filters implemented: `re_replace`, `replace`, `regexp`, `querystring`, `trim`, `tolower`/`tolowercase`, `toupper`/`touppercase`, `append`, `prepend`, `split`, `urlencode`, `urldecode`, `htmldecode`, `htmlencode`, `validate`, `validfilename`, `diacritics`, `reverse`, `jsonjoinarray`, `hexdump`, `strdump`, `dateparse`, `timeparse`, `timeago`, `reltime`, `fuzzytime`. Cardigann spells the case filters both ways and real definitions use both spellings, so both are registered rather than one being treated as canonical. Filter `args` are themselves rendered as templates before use.
- **Filters match Jackett's semantics, quirks included**, because definitions are written and tested against Jackett — a "better" filter silently produces values the definition's author never saw. Specifically: `regexp` yields `""` when nothing matches or the pattern has no capture group (returning the input instead would pass a whole HTML blob through as a field value); `validate` is a token *intersection* joined with commas, not an all-or-nothing check, and an empty result is normal; `split` and `trim` act on the **first character** of their argument only, mirroring `String.Split(sep[0])` and `String.Trim(cutset[0])`, and `split` wraps a negative index; `re_replace` translates .NET replacement syntax (`$1x`, `$&`) into Go's via `goReplacement`, since Go would read `$1x` as a group named `1x`; `diacritics` **requires** its `replace` argument and errors on anything else, as Jackett raises rather than guessing — folding regardless applies a transformation the definition never asked for, and definitions in Jackett's repository pass it; `htmlencode` mirrors `WebUtility.HtmlEncode` (`&quot;`, and numeric entities for the Latin-1 supplement) rather than Go's `html.EscapeString`; `urlencode`/`urldecode` use .NET's unreserved set (`!*()` literal, `~` escaped) and round-trip through the definition's declared `encoding`, so a windows-1251 tracker gets cp1251 bytes. `timeago`/`reltime` follow `FromTimeAgo`: every number/unit pair in the text contributes (`"1 day 2 hours ago"` is 26h, not 2h), abbreviations (`3h`, `5 min`, `2 wks`, `mo`) are understood, and `"now"` resolves. `dateparse`/`timeparse` are one filter in Jackett, and its layout argument may be written **either** as a .NET custom format (`yyyy-MM-dd`, `dd/MM/yyyy`) or as a Go layout (`2006-01-02`) — real definitions carry both, so `parseDeclaredLayout` tries them in Jackett's order, converting a .NET format with `goLayoutFromDotNet`. Four traps there, all of which produce layouts that silently fail to parse or quietly misread: a .NET fraction token is **only** the digits (`ss.fff`), so it maps to `000`/`999` and takes its separator from the literal `.` already in the format — emitting one with the token yields `05..000`; and .NET copies any character it has no specifier for straight through as a literal, so an unrecognized letter must **not** be rejected, or the very common `yyyy-MM-ddTHH:mm:ss` is refused over its `T`. A repeated specifier is **one** token, not a longest-match prefix plus the remainder: `matchDotNetToken` consumes the whole run (`ParseRepeatPattern` in .NET's own parser) and clamps it to the longest entry the table defines, so `h ttt` is a single full designator rather than `tt` followed by a stray `t` demanding a second one-letter designator, and `hhh`/`ddddd` read the same as `hh`/`dddd`. `K` is excluded from the run because .NET does not repeat it. Clamping is exact everywhere but `y`, where .NET pads to the run's own width and Go has no five-digit year token; no real definition writes one. Go's tokens are fixed-width, so .NET's single `t` (one character, `A`/`P`), single `z` (a one-digit offset, `+5`) and single `y` (a year without its leading zero, `9`) cannot be represented directly. Refusing them leaves those layouts parsing nothing, so `dotNetLayout` **widens the value** to meet the token — adding the `m`/`M` or the leading zero the wider Go token expects. No fix-up may assume where the token sits, and no context rule can decide it either — a format's own literal can look exactly like the token, as `'P' t hh:mm` does against `P A 07:30`. So `widenedValues` generates a candidate per plausible position and lets the **parse** choose: every other part of the layout still has to match, so a variant that widened the wrong character simply fails. The position tests only have to be a superset of the real ones. `dotNetLayout` counts each narrow token rather than flagging it, because a format may carry one twice (`t h t`) and one widened position is then not enough; `widenAt` runs once per occurrence, and a position already widened no longer matches, so the passes compound into the combinations instead of repeating themselves (`maxWidenedValues` caps the total). Whether the **unwidened** value is itself a candidate follows .NET's own leniency and differs per token: a single numeric specifier there accepts one digit or two, so `z` reads `+05` and `y` reads `09`, but `t` is the designator's *first character* rather than an abbreviation of it, so `7 PM` is a genuine mismatch for `h t` and must not be quietly accepted through Go's two-character `PM`. A format whose **literal** text Go would read as a token — `yyyy 'January' dd`, `yyyy '15' dd`, or a bare `Jan` run — is refused outright by `literalIsInert`, because Go cannot escape a literal and the layout would otherwise accept any month or hour where .NET demands those characters. It needs **three** reference instants: the two `layoutHasDate` uses share a clock by design, so a literal `15`, `04`, `05` or `PM` renders identically for both and reads as ordinary text. `referenceElsewhere` differs in every component a token can render — including fractional seconds and zone — which is what catches them, and incidentally catches a literal like `GMT+5`, whose `5` is Go's seconds token. Refusing is right there and wrong for the tokens: a narrow token still parses correctly with a fix-up, while a literal cannot be represented at all, and a wrong parse is worse than none. And .NET compares an AM/PM designator case-insensitively while Go's `PM` matches only the uppercase pair, so `parseEitherCase` retries with `pm`: 1337x lists `7am Sep. 14` against a `htt MMM. d` layout. Being permissive about *literals* costs nothing because the conversion is only ever attempted: `looksLikeDotNetLayout` keeps Go layouts away from it, and one that slips past converts to nonsense, fails to parse, and falls back to being read as Go's. Don't reduce this to `time.Parse`: `dd/MM/yyyy` then fails and a heuristic guess reads `03/02/2024` as 2 March instead of 3 February. A value the declared layout does not fit is left **unchanged**, as Jackett leaves it — the date field is resolved heuristically later in `torrentFrom` regardless, so nothing is lost, and a guess must not be written into a value a later filter in the chain would read. Whatever a layout leaves out, `resolveMissingDate` supplies the way .NET's `ParseExact` does and Go does not: a layout with a date but no year takes the current year, stepping back one when that lands in the future (Go layouts only, matching Jackett's own asymmetry), and a layout with **no date at all** is a time of day dated to **today** — a tracker printing bare times for today's releases, which Go would otherwise date to 1 January in year zero. The step-back is deliberately not applied there: a release stamped minutes ahead of us by clock or timezone skew means a moment ago, not a year ago. Zone-less values are parsed **in the local zone**, not UTC: a tracker printing no offset means its own wall clock, which is how Jackett's date utilities read it, and `time.Parse` would put the stored instant hours out on any non-UTC host. That applies to both `parseDeclaredLayout` and the heuristic `parseUnknownTimeValue` (`dateparse.ParseIn`), and an explicit offset in the value still wins. It is why several tests build their expected value with `time.Local` rather than a fixed `...Z` string, and why the deliberate `time.Local` uses carry `//nolint:gosmopolitan`. `layoutHasDate` tells the two apart by *formatting* two instants that differ only in date and comparing the results — reading Go's date tokens out of a layout string means reimplementing `nextStdChunk`, and they overlap in ways that defeat a plain search, since `2` is a day but also sits inside `2006`. `fuzzytime` is `FromUnknown`, and the order in `parseUnknownTimeValue` is load-bearing: RFC1123Z, bare Unix timestamp, `now`, `ago` (gated on the word, or a date merely holding a number and a word reads as "N units ago"), today/yesterday/tomorrow, a named weekday meaning the one just gone, a date missing its year (this year, stepped back if that is in the future), **a bare time of day meaning today**, and only then the general parser. The time of day has to come before that parser rather than after: `dateparse` reads `7:05pm` as the 1st of July in **year zero** and reports no error, which stores as a release two thousand years old — 1337x's `date_today` field is exactly this shape. A year-zero result from the final fallback is rejected for the same reason. These live in `pkg/scraper/fuzzytime.go`, where a time of day is a `clockTime` of its components rather than an elapsed duration: adding `03:30` to local midnight yields **04:30** on the day the clocks go forward, because that hour does not exist, so the instant is built with `time.Date` instead. The weekday walk steps over whole days at midnight and applies the clock once at the end for the same reason.
- **Cardigann has two kinds of filter and they are not interchangeable.** `filterRegistry` holds the *value* filters, which rewrite one field (Jackett's `applyFilters`). `search.rows.filters` holds the *row* filters, which decide whether a scraped row is kept at all (Jackett's `ParseRowFilters`), and they live in `pkg/scraper/rowfilters.go` behind `skipRow`. Jackett supports exactly two row filters: `andmatch` and `strdump`. There are also two *value* dump filters, `hexdump` and `strdump`, whose only effect is their log line — which is why `filterFunc` takes a `filterEnv` carrying a logger beside the charset. Registering them as no-ops passes the value through correctly and still leaves a definition diagnosing an encoding problem with nothing to read. `strdump` logs the row **as served**, XML-escaped for the XML case (`writeXMLEscaped`) so a row whose text carries `&` or `<` dumps as the document it actually is rather than as markup that never existed — — `resultRow.debugString`, implemented by all four row types — because the filter exists so a definition's author can see what their selectors are addressing; logging extracted values instead would remove the only thing it provides.
- **`andmatch` is a row filter and must never be added to `filterRegistry`.** As a value filter it would rewrite a field; as a row filter it drops releases whose title lacks a query word, which is what it is for — ilcorsaroblu and girotorrent sit on trackers that OR the query terms together, and without it every unrelated release comes back as a result. `matchQueryStringAND` mirrors Jackett's: split on non-word characters, ignore single characters and `and`/`the`/`an`, compare case-insensitively, and honour the optional character limit for a tracker that lists truncated titles. Use `splitQueryWords` rather than Go's `\w`, which is ASCII-only and would shred a Cyrillic query into single characters that then all get ignored. The filter stands down for a search by an external id the definition advertises (`idSearchSupported`), since the tracker matched on the id and the titles have no reason to carry the keywords. Those gates are **Jackett's, quirks included** and must not be tidied into "each id checks its own capability": a douban or trakt search is gated on the *imdb* capability, a tvmaze or rage search on the *tv-search imdb* capability, and that last one comes from the definition-level `caps.allowtvsearchimdb` boolean rather than from the tv-search parameter list. They read the **declared** `caps.modes` rather than `SearchModes`, whose generic fallback exists to advertise a keyword search and would silently widen every gate. A row that one filter rejects still goes through the rest of the list — a definition pairing `andmatch` with a following `strdump` wants to see what was dropped — so `skipRow` accumulates a flag rather than returning early. `reverse`, `tolowercase` and `touppercase` genuinely are not Jackett filters, but they only transform a value a definition explicitly asked to transform, so they stay.
- **The definition's `encoding` reaches the filters through an unexported `templateData.encoding` field.** It is unexported on purpose: `text/template` cannot reach an unexported field, so the charset rides along to `urlencode`/`urldecode` without becoming a variable a third-party definition could read.

- **Caps come from the definition**: `searchingCaps` renders `caps.modes` (via `scraper.SearchModes`, which falls back to a generic keyword-search set when a definition declares none) into the Torznab `<searching>` element, so a music or ebook tracker is advertised as able to serve those searches. Don't go back to a hardcoded set.
- **FlareSolverr carries no per-request headers, and `warnUncarriedHeaders` says so**: `fetch` hands a FlareSolverr-backed search straight to `scrapeWithFlareSolverr`, before the branch that applies `search.headers`, the default User-Agent and the redirect policy — and that is not an oversight to tidy up. The request is made by a real browser, which supplies its own headers, and FlareSolverr v3 removed the option to override them, so there is nothing to forward and forwarding it anyway would only look like support. Definitions declaring `search.headers` are common, so the silence was the problem: a warning is logged once per tracker (`scrapeState.warnedFlareHeaders` — once per *tracker*, not per search, since a line repeated on every poll is one an operator stops reading). `SearchPath.FollowRedirect` is inert for the same reason, the browser following redirects itself. Downloads bypass FlareSolverr entirely and **do** apply the headers, so the two paths genuinely differ.
- **FlareSolverr mirrors the definition's HTTP method**: `scrapeWithFlareSolverr` issues `request.get` with the inputs in the query string for a `method: get` search path and `request.post` otherwise. Always POSTing means a GET definition's inputs never reach the tracker. FlareSolverr also gets its own `http.Client` (`flareSolverrTimeout`, 3m) rather than sharing the scraper's 30s one, since driving a browser through an anti-bot challenge routinely takes longer than a plain fetch.

- **Every advertised mode must be servable**: `handleCaps` derives `<searching>` from `caps.modes`, and `ServeHTTP`'s `t=` switch must accept a value for each mode it can advertise (`music`/`audio`/`book` as well as `search`/`tvsearch`/`movie`, hyphenated and unhyphenated). Advertising a mode the switch rejects makes a client take Jacklet up on an offer it then answers with 400. `TestTorznabHandler_AcceptsEveryAdvertisedMode` pins the two together.
- **Row extraction is format-agnostic**: `resultRow` (`pkg/scraper/rows.go`) abstracts the three response formats a definition can declare, so `extractFields` is written once. A search path declaring `response: {type: json}` selects rows and fields by dotted key path instead of selector; `jsonScalar` formats numbers without scientific notation, since an id or byte count scraped as `1.2345e+04` is useless.
- **`response: {type: xml}` has its own parser, and cannot reuse goquery** (`pkg/scraper/xml.go`, in practice always an RSS feed). The definitions keep writing CSS selectors, but an HTML parser cannot serve them: it lowercases element names, so a definition's `pubDate` never matches `<pubDate>`; and `<link>` is a void element in HTML, so the text of an RSS `<link>https://…</link>` is parsed *outside* the element and comes back empty — which is the details URL for many of them. Jackett reaches for a separate XML parser for the same reason. So `parseXML` builds a tree with `encoding/xml` and `selectXML` implements the selector subset those definitions actually use: element names, `[attr]` and `[attr=value]` predicates, and the descendant and child combinators, all matched **case-sensitively** as XML defines them. A selector outside the subset matches nothing rather than pretending. Two details that are easy to undo by accident: the decoder is given a pass-through `CharsetReader`, because `fetch` has already decoded the body to UTF-8 and a feed still declaring `windows-1251` would otherwise be refused; and a namespaced `<torznab:attr>` is stored under its local name, which is what `[name=seeders]` selects against.
- **A required field that doesn't match drops the row**: `extractFields` returns `ok=false` unless a field is declared `optional`, matching Cardigann rather than storing a row with a hole in it. Be careful changing this: it silently changes how many results a definition yields.
- **Login**: `pkg/scraper/login.go` implements Cardigann's `form`/`post`/`get`/`cookie` methods, adopting hidden form fields (CSRF tokens) from the login page. Credentials come from the definition's own `username`/`password` settings via `JACKLET_CONFIG_DIR`, so no new configuration mechanism was added. A successful login is trusted for `loginValidity` (30m) rather than re-tested every scrape; a failed fetch invalidates it so the next scrape re-authenticates. A `captcha:` block is reported as `ErrCaptchaRequired` rather than attempted.
- **A nil config value is an empty string**: `mergedConfig` maps a setting with no default, and an override written as a bare `password:` with no value, to `""`. Formatting a nil `any` with `%v` yields the literal text `"<nil>"`, which would otherwise be sent to a tracker as a password.

**Still not implemented**: the **top-level** `followredirect`, which in Jackett rewrites the configured site URL when a login test is redirected to another domain — Jacklet answers a moved site with mirror failover instead, and does not rewrite an operator's configuration behind their back.

The template layer itself has no known gap. The one expression in Jackett's repository that does not render is not a gap: `1337x.yml` writes `(eq .Config.disablesort .False))` with a doubled parenthesis, which Jackett's regex substitution tolerates because it never parses it. Render the whole corpus before and after a change here, rather than reasoning about which gap matters. Also: any Cardigann template variable beyond `.Config`/`.Keywords`/`.Categories`/`.Query`/`.Result`/`.Today`/`.True`/`.False` (`.Env` and `.Query.APIKey` both deliberately — see above); CAPTCHA handling (fundamentally hard for a headless service with no UI for a human to solve one, so a definition declaring one is refused outright); an HTTP/SOCKS proxy for outbound requests; and separate `tv-search`/`movie-search` definition blocks (Jacklet's `Tracker.Search` models one shared block used for every search type, which is what Cardigann definitions in general actually do in practice, but the format does allow per-mode overrides that Jacklet won't parse).
